Chute Buddies

Building a 3D co-op multiplayer game in Godot 4 — from an empty project to hosting a lobby, loading levels together, throwing junk at a chute, and showing who won. Every step runs on its own; nothing is left half-finished until later.

What you end up with

Four friends host and join a lobby. Everyone drops into a level full of junk. You grab a crate, chuck it at the chute, and it scores for whoever threw it. Clear the level and the whole group loads the next one. After the last level, a results screen shows who hauled the most. Someone can quit and rejoin halfway through and the game keeps running.

  • Godot 4.4 (anything 4.3+ works), GDScript
  • ENet peer-to-peer with one player acting as host
  • MultiplayerSpawner, MultiplayerSynchronizer, and hand-written RPCs
  • No art assets required — everything is CSG boxes and capsules

How to read this

Every part ends with something you can run. Code is never written against a file that doesn't exist yet. When a later part needs to change an earlier file, you get a pink block that tells you exactly where the new lines go:

Edit res://player/player.gd — add this below _ready()

Blocks that look like this are insertions into a file you already wrote. Everything else is a complete new file you can paste whole.

Code block headers are labelled NEW for a file you're creating, EDIT for a change to an existing one, and EDITOR for something you do in the Godot editor rather than in a script.

The shape of the thing

Before any code, here's the architecture, because most Godot networking pain comes from getting this wrong rather than from the RPC syntax.

Main.tscn  ..................  loaded once, never unloaded
 ├─ World
 │   ├─ LevelHolder .........  level geometry gets swapped in here
 │   ├─ Players .............  MultiplayerSpawner target
 │   └─ Props ...............  MultiplayerSpawner target
 ├─ PlayerSpawner
 ├─ PropSpawner
 └─ UI
     └─ ScreenHolder ........  menu / lobby / HUD / results swap here

Autoloads
 Net ........................  sockets, peer list, who is in the session
 GameFlow ...................  match state: which level, scores, who's ready
 Levels .....................  the list of levels, as data
Why one persistent scene

The obvious approach is change_scene_to_file() to move between menu and game. It fights networking constantly: a MultiplayerSpawner replicates its nodes to any peer that connects, and if that peer's scene tree doesn't contain the spawn path yet, the spawn is dropped and you get errors in the console with no player in the world.

By loading Main.tscn once at startup and swapping contents instead of scenes, the paths /root/Main/World/Players and /root/Main/World/Props exist on every peer from the moment the game launches. Late joins stop being a special case. This one decision removes an entire category of bug, so we make it first.

Three rules the whole tutorial follows:

  • The host is the source of truth for scores, level progression, and who is holding what. Clients ask; they don't decide.
  • Each player moves their own character. Movement is client-authoritative — it feels good, it's cheap, and for a game you play with friends it's the right trade. We'll be explicit about what that costs.
  • Authority is per-node. A player node is owned by the client it belongs to. A junk crate is owned by the host. Getting this straight is most of the work.

Why the camera rig yaws instead of the body

CamRig is a child of Player, but we never rotate Player itself. If the root rotated, the camera would be dragged around every time the character turned to face a new direction, and looking around would fight the movement. Instead: CamRig holds the look direction, Body holds the facing direction, and they only relate through _wish_direction(). When we replicate the player over the network in Part 7, this also means we sync exactly two things — the root's position and Body's rotation — and the camera stays local to whoever owns the character.

PART 4The network layer

This part adds one autoload with one job: open a socket, and keep an agreed list of who is in the session. It knows nothing about levels, scores, or players. That separation is what keeps the rest of the game testable.

How the roster stays in sync

The host owns the roster. There is no merging, no partial updates, no ordering problems:

  1. A client connects and tells the host its chosen name.
  2. The host adds it to the roster dictionary.
  3. The host broadcasts the entire roster to everyone.

A client that joins in the tenth minute of a match gets the full picture in its first packet, because there's only ever one kind of roster message.

Register it: Project → Project Settings → Autoload, path res://autoload/net.gd, node name Net.

Reading the RPC annotations

@rpc("any_peer", "reliable") on _request_join means any client is allowed to call it on another peer, and the packet is guaranteed to arrive. It is only ever aimed at the host, via rpc_id(1, ...) — peer 1 is always the server in Godot.

@rpc("authority", "reliable") on _receive_roster means only the node's authority may call it. Autoloads default to an authority of 1, so this is a compile-time-ish guarantee that a client can't forge a roster. Note there's no "call_local": when the host broadcasts with .rpc(), the host doesn't run the function on itself, which is correct here because the host already edited roster directly.

An RPC only works if the node exists at the same path on both peers. Autoloads always do — they're at /root/Net everywhere. This is why session-level messaging lives in an autoload and not on some node inside the level.

PART 6Match state and the level handshake

Here's the problem this part solves. The host presses Start match. If it immediately spawns players into level 1, the clients haven't loaded any level geometry yet — the spawn arrives, characters appear over nothing, and everyone falls out of the world while the floor loads underneath them.

So loading a level is a two-step conversation:

HOST                                 CLIENT
  |  state = LOADING, level = 0        |
  |---------------------------------->|  build_level(0)
  |                                    |  report_level_ready()
  |<----------------------------------|
  |  (waits for every peer in roster)  |
  |  state = PLAYING                   |
  |---------------------------------->|
  |  spawn everyone                    |

Nothing enters the world until every peer says it's standing on a floor. The same handshake is what makes joining halfway through a match work in Part 8, so it's worth getting exactly right.

The GameFlow autoload

Register it as an autoload named GameFlow, below Net in the list — GameFlow._ready() connects to a Net signal, so Net has to exist first.

Why GameFlow emits signals instead of spawning

spawn_all_requested could just as easily be players_root.add_child(...) right here. It isn't, because an autoload has no business reaching into the scene tree at a hardcoded path — the moment you rename a node, an unrelated file breaks.

GameFlow answers "what should be true right now". Main answers "how do I make that true in the tree". When you later add spectators, or a title screen that shows a demo level, the state machine doesn't change at all.

PART 7Spawning players over the network

Three things have to be true for a networked character:

  1. The same node exists on every peer, at the same path, with the same name.
  2. Exactly one peer decides where it is — its authority.
  3. Everybody else receives that position instead of computing it.

Why spawn_function instead of the Auto Spawn List

With the Auto Spawn List, the host adds a child and the spawner replicates "instantiate scene 0 and call it 1234". Any property the host set before adding — like the spawn position — is not part of that message. You'd have to follow up with a separate RPC, which can arrive before the node exists.

spawn_function replicates the argument. Every peer runs _build_player with the same dictionary, so the character exists with the right name at the right coordinates in one atomic step. Keep the data small — it goes over the wire on every spawn.

Run two copies

Host, join, start. Both players appear at different spawn markers, each window controls its own capsule, and you can watch the other one run around. Press Escape to free the mouse, click back in to recapture.

Movement will look slightly steppy on the remote character — that's the synchronizer delivering discrete positions with no interpolation between them. Part 12 fixes it in four lines. Don't fix it now; it's much easier to reason about the raw signal while you're still adding features.

The honest cost of client-authoritative movement

Each client tells everyone where it is, and nobody checks. A modified client can teleport, fly, or walk through walls. For a game you play with friends on a private host, that's a fine trade for movement that feels perfect on every connection.

Notice that this is a per-node decision, not a project-wide one. Junk crates in Part 9 are owned by the host precisely because that's where cheating would actually ruin the game — scoring. You can move any single node's authority to the host later without touching the rest of the architecture, which is the payoff for keeping authority explicit.

Trace what happens when someone joins during level 2:

  1. Net receives their name, adds them to the roster, broadcasts it.
  2. GameFlow._on_peer_joined gives them a score of 0 and sends them the current state — PLAYING, level 1.
  3. On the newcomer, Main._on_state_changed sees built_level_index is -1 and the host says 1, so it builds the garage and reports ready.
  4. The host is in PLAYING, so it spawns just that one player.
  5. The spawner replicates every character and crate that already exists to the new peer, into paths that have existed since their game launched.
This is the payoff from Part 1

Step 5 is the one that breaks in most Godot projects. A MultiplayerSpawner sends its existing spawns to any peer that connects, and if World/Players doesn't exist on that peer yet — because they're still sitting in a separate menu scene — those spawns are dropped with an error and the newcomer sees an empty world. Because Main.tscn is never unloaded, there is no window during which the path is missing.

When someone leaves

A disconnect fires multiplayer.peer_disconnected on the host, which Net turns into peer_left, which GameFlow turns into despawn_player_requested, which Main turns into queue_free() on their character. Freeing a spawned node on the host tells every client to free their copy — you don't have to send anything yourself.

The other half is the host quitting. Net._on_server_disconnected already calls leave() with a message, which clears the roster, fires session_ended, and sends everyone back to the main menu with an explanation. GameFlow._reset is on the same signal, so state and scores are wiped at the same moment.

PART 9Picking up and throwing junk

Movement is owned by each client. Junk is owned by the host, and the reason is scoring: a crate's position decides who gets a point, so a client is never allowed to decide it. Clients ask; the host answers by changing state that everyone then receives.

Why clients don't simulate physics at all

Two peers running the same rigid body will diverge — floating point, frame timing, and slightly different contact orders guarantee it. Then the synchronizer yanks the crate back to the host's answer and you get jitter.

Setting freeze = true with FREEZE_MODE_KINEMATIC on every non-host peer removes the fight entirely: the crate becomes a thing that is told where it is, while still colliding with characters locally so you can stand on it. All the interesting physics happens once, on the host.

Only the host clears the world

It is tempting to have every peer free its own copies — it looks tidier and it's instant. Don't. Those nodes belong to the MultiplayerSpawner, and when the host's despawn message arrives for a node a client already deleted, you get errors and, in the worst case, a client that misses the next spawn. Let replication do the deleting, in both directions.

Note also that level_cleared() is guarded on state == PLAYING. Clearing the world fires _on_prop_removed six times in a row, but by then the state is already LOADING, so the level can't advance twice.

Why 1.0 - exp(-k * delta)

The usual lerp(a, b, 0.2) converges at a rate that depends on frame rate, so the same game looks different at 60 and 144 fps. This form is frame-rate independent: k is a speed in units of "per second" and the result is identical however often you sample it. It's worth using everywhere you smooth something.

Junk can get the same treatment with the same three lines — it matters less because thrown crates move on predictable arcs, but a carried crate held by a laggy player is noticeably nicer with it.

The failure cases worth handling

What happensWhat the game does now
Host quits mid-matchserver_disconnected → main menu with a message. Handled in Part 4.
Client quits mid-matchCharacter despawns, held crate drops, score entry removed. Parts 8 and 9.
Client quits while everyone waits on them to load_check_everyone_ready() re-runs on peer_left, so the match proceeds. Part 8.
Wrong IP typedconnection_failed → main menu, "Could not reach that host."
Port already in usehost() returns an error, menu explains it.
Last crate rolls somewhere unreachableNot handled. The level can never be cleared.

That last row is the one real gap. The cheapest fix is a kill plane: an Area3D under the level with its mask set to junk, whose body_entered respawns the crate at a random JunkSpawns marker on the host. You now have everything needed to write it — it's the same shape as chute.gd, calling global_position = ... instead of queue_free().

Two more worth adding once the core is solid:

  • A join timeout. connection_failed can take a long while on an unroutable address. Start a SceneTreeTimer when join() is called and give up after five seconds if in_session() is still false.
  • A crate limit per level. Right now the level is over when the crates run out, which means the last one decides the pace. A par time or a target score per level from the Levels registry gives you more control — and it's the reason that registry has a dictionary per level rather than a bare path.

Playing with actual friends

ENet uses UDP. Everything in this tutorial works over LAN with no configuration — the host reads its local address (something like 192.168.1.x) and everyone types it into the address field.

Over the internet, the host needs UDP port 24565 forwarded to their machine, or you all need to be on the same virtual LAN. Godot ships a UPNP class that can ask a router to open the port automatically; it works often enough to be worth trying and never often enough to rely on. Do it on a thread — UPNP.discover() blocks for seconds.

Before you share a build

Everything here trusts the host completely and the clients partially. That's correct for playing with friends and wrong for a public game. If you ever open this to strangers, the movement authority in Part 7 is the first thing to move to the host, and _request_join in Part 4 needs a check that the same peer can't register twice.

Where you ended up

Three autoloads with one job each, a persistent scene that owns the tree, and gameplay nodes that never reach across the codebase to find each other. Adding a level is one line in Levels.LIST. Adding a new prop type is a scene, a script with _enter_tree setting authority to 1, and a spawn function. Adding a new match state is an enum value and a branch in refresh_screen.

The parts that took real thought — the two-step level handshake, spawning through a function instead of a scene list, one persistent root — were all about the same thing: making sure that when a message arrives, there is somewhere for it to land.

Written for Godot 4.4. Godot's own High-level multiplayer documentation is the reference for anything here you want to go deeper on, particularly MultiplayerSynchronizer visibility filters, which are how you'd stop sending a peer things it can't see.
