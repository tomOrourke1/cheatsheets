01

Make the project

cargo

Nothing Bevy-specific yet — a normal Rust binary crate with one dependency.

Then add the profile block. Without it, debug builds run at a few frames per second and you will think you broke something.

The first cargo build compiles the whole engine and takes several minutes. Every build after that is fast. Go make tea.

02

Open a window

App

An App is a list of plugins and a list of systems. DefaultPlugins brings the window, renderer, input and asset server.

cargo run

A 960×640 window titled “Box Runner”, filled with dark blue-grey. Close it with the window button.

..default() is ..Default::default(), re-exported by the prelude. You will type it constantly — Bevy structs are wide and you usually only care about two fields.

03

Draw the player

Camera2d · Sprite

Two things are needed to see anything in 2D: a camera, and an entity with a Sprite. Without a camera you get a blank window and no error.

Add the constants at the top of the file, under the use line.

Add a marker component and two startup systems.

And register them in main, just before .run().

cargo run

A yellow rectangle sitting above the centre of the window. The world origin (0, 0) is the middle of the screen, and +Y is up.

Sprite::from_color needs no image file, which is why this guide uses a box instead of artwork. Swap in Sprite::from_image(asset_server.load("sprites/hero.png")) whenever you have a PNG in assets/.

04

Move left and right

ButtonInput

Keyboard state lives in a resource. You poll it; there is no callback.

Two new pieces of data: how fast the player is going, and what the keyboard is asking for.

Give the player a Velocity when it spawns.

Read the keyboard into the resource, then use it to drive the transform.

cargo run

A / D or the arrow keys slide the box left and right. It drifts off-screen forever — gravity and walls come next.

Always multiply movement by time.delta_secs(). Without it your player moves faster on a 144 Hz monitor than a 60 Hz one.

Single<..> means “exactly one entity matches”. If none match — or two do — the system is skipped instead of panicking, which is exactly what we want once the player only exists during gameplay.

05

Gravity and a floor

FixedUpdate

Physics moves to FixedUpdate, which runs at a constant rate regardless of frame rate. Jump height stays the same on every machine.

A collider is just a size. Everything solid gets one, including the player.

The whole collision system, in one function. Move on one axis, push out of anything you hit, then repeat for the other axis. Doing the axes separately is what stops you snagging on corners.

move_player is now redundant — delete it. Split the old work in two: read_input stays in Update, and a new apply_input feeds the velocity inside FixedUpdate.

Give the player its collider and grounded flag, and put a floor in the world.

cargo run

The box falls, lands on the grey slab, and stops. A / D walks it along the surface, and it can no longer leave the platform through the side.

Why .chain()? Systems run in parallel by default. Chaining forces apply_input to finish before move_and_collide starts, so velocity is always set before it's used.

06

Jumping

input buffering

One line of physics and one genuinely subtle problem.

cargo run

Space or W launches the box upward; it arcs back down and lands. Holding Space doesn't make it fly — just_pressed is one frame only.

Why the jump_queued flag exists. Update runs once per frame; FixedUpdate runs zero, one, or several times per frame depending on how the frame rate lines up with the fixed rate. If you called keys.just_pressed(..) directly inside FixedUpdate, a jump would be dropped on frames with no fixed step and fire twice on frames with two. Sampling in Update and consuming in FixedUpdate fixes both. This is the single most common source of “my jump sometimes doesn't register”.

Feel worth tuning: raise GRAVITY for a snappier arc, raise JUMP_SPEED to go higher. Real platformers also apply extra gravity while falling, and allow a jump for a few frames after leaving a ledge (“coyote time”). Both are small additions to apply_input once the basics work.

07

Build a level

iteration

The collision code already handles any number of solids. Adding a level is now just adding entities.

And catch the player if they fall off the world.

cargo run

Five platforms. You can hop between them, land on the tops, bump your head on the undersides, and falling off the edge puts you back at the start.

That array is a level format. Loading it from a RON or JSON file in assets/ instead of hardcoding it is a good next exercise, and the loading code is about ten lines.

08

Add app states

bevy::state

A menu and a game are two modes. States give you “run this only while playing” and “clean this up on the way out” for free.

Tag everything the gameplay spawns so it disappears when you leave. DespawnOnExit does the bookkeeping.

Do the same inside the spawn_level loop, adding DespawnOnExit(AppState::Playing) to each platform. Then rewire main: level and player move off Startup and onto OnEnter, and the gameplay systems get a run condition.

The camera stays on Startup — it belongs to the app, not to either mode.

cargo run

An empty window. The app starts in Menu, so nothing spawns. That's correct — the menu is the next step.

Systems that use Single<.. With<Player>> would already skip themselves without a player around, so the run conditions here are belt and braces. They're still worth writing: they document intent, and they cost nothing.

09

The menu

bevy::ui

Bevy UI is flexbox. Node is the box; colour and text are separate components on the same entity. This layout is one full-screen column, centred.

cargo run

A title, a hint line, and a Play button that lightens on hover. Clicking it clears the menu and drops you into the level.

Why the button is spawned separately. children![..] builds children inline, but you can't attach an observer to something inside that macro. Spawning the button as its own entity with ChildOf(root) gives the same layout while leaving room for .observe(..). It still appears after the two text children, because children! ran first.

Observers are one way to handle a button. The other is polling Query<(&Interaction, &mut BackgroundColor), (Changed<Interaction>, With<Button>)> in a normal system. Observers suit one-off behaviour; polling suits “style every button the same way”.

10

Close the loop

HUD

A way back out, and an on-screen reminder of the controls.

cargo run

Play → jump around → Esc → back at the menu with everything cleaned up → Play again spawns a fresh level. That's a complete game loop.

A Text entity carrying a Node is UI text, positioned in screen space. A Text2d entity is world text that moves with the camera. Reaching for the wrong one is a common half-hour.

12

When it won't compile

troubleshooting

Bevy's type errors are long. These four cover most of what goes wrong early.

ErrorCause and fix
temporary value dropped while borrowedYou wrote let app = App::new().add_plugins(..);. The chained methods return &mut App, not App, so you bound a borrow of a temporary. Write let mut app = App::new(); on its own line, then call the methods on app.
(A, B, C, ...) is not a BundleOne member of a spawn tuple isn't a Component. The compiler writes the full type to a file in target/debug/deps/*.long-type-*.txt — read it. If it's still unclear, delete tuple members until it compiles, then add them back one at a time.
Query<&mut T> conflicts with Query<&T>Two params in one system touch the same component and Bevy can't prove they're disjoint. Add With/Without filters that separate them — this is why move_and_collide uses Without<Player> on the solids query.
the trait bound ... FontSize is not satisfiedfont_size takes FontSize::Px(24.), not a bare 24., as of 0.19. Likewise font takes a FontSource, so an asset handle needs .into().

And two that compile fine but produce nothing:

SymptomCause
Blank window, no errorsNo camera. Camera2d for sprites and UI, Camera3d for meshes.
A system never runsA Single or Res parameter didn't resolve, so Bevy skipped the system silently. Check the entity exists and the resource was inserted. Swapping Single<T> for Query<T> temporarily will tell you which.

Compiler errors that mention types you didn't write usually come from a macro. Run cargo build 2>&1 | head -40 — the first error is nearly always the real one, and everything after it is fallout.

next

The most useful habit from here: when something doesn't work, find the matching official example at bevy.org/examples and read its source. They're pinned to the release you're on and they always compile.
