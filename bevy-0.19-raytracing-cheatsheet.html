@binding(0) · foundation

Project setup

Bevy compiles slowly if you leave the defaults alone. The two profile overrides below matter more than anything else you will do this week — they build your dependencies optimised while keeping your own crate fast to recompile.

For fast iteration, link Bevy dynamically instead of statically. Do not ship a release build with this flag — it requires the .so/.dll to sit next to your binary.

Changed in 0.19 — feature collections

The 3d, 2d and ui collections no longer imply audio, and 3d/2d no longer imply ui. If you build with default-features = false and your audio or UI silently vanished, add those features back explicitly.

The smallest app that draws something

A 3D scene needs three things on screen: a camera, a light, and geometry. Everything else in Bevy is a component you add to those.

Required components

You never spawn a Transform alongside Mesh3d because you have to — Mesh3d requires it, so Bevy inserts a default one. Same for Camera3d and its Camera, Projection, Msaa. Spawn a component explicitly only when you want to override the default.

@binding(1) · assets

Loading .glb models

Bevy reads .gltf and .glb out of the box. A single glTF file is not one asset — it is a bundle of sub-assets (scenes, meshes, materials, animations) that you address individually with a label.

Assets resolve relative to an assets/ folder next to Cargo.toml:

Changed in 0.19 — this is the big one

The old bevy_scene crate was renamed to bevy_world_serialization to make room for the new BSN scene system, and its types were renamed with it. To spawn a glTF scene you now use WorldAssetRoot, not SceneRoot. Nearly every tutorial online still shows the old name.

Loading is asynchronous. The entity exists immediately; its children appear a frame or several later. That is why anything that inspects the model has to wait for a signal rather than run in Startup.

Addressing sub-assets

GltfAssetLabel builds the path#Label string for you. Use the enum rather than hand-writing the string — it survives renames.

Changed in 0.19 — material sub-assets

Loading a material label used to hand you a Handle<StandardMaterial>. It now gives you a Handle<GltfMaterial>, which faithfully mirrors the file. Append /std to get the renderable StandardMaterial. Also gone: the MorphTarget label — morph targets live inside the Mesh now, via Mesh::get_morph_targets.

Reacting once the model is actually in the world

Attach an observer to the spawned entity. WorldInstanceReady fires when the hierarchy has been built, which is the only safe moment to walk it. This pattern is the backbone of everything else on this page — adding colliders, swapping materials, and tagging meshes for raytracing all hang off it.

If your model is invisible
  • No light in the scene, or the model is behind the camera. Add an AmbientLight resource while you debug.
  • Scale mismatch — glTF is metres, and CAD exports are frequently 100× or 0.01× off. Try Transform::from_scale(Vec3::splat(0.01)).
  • .gltf files reference external .bin and texture files by relative path. Copy the whole folder, or use .glb, which embeds everything.
  • Check for load errors — run with RUST_LOG=bevy_asset=debug.
@binding(2) · hardware raytracing

Full raytracing with Solari

bevy_solari is Bevy's realtime pathtraced lighting system. It replaces shadow maps, screen-space AO and screen-space reflections with actual traced rays, using ReSTIR for direct and indirect light plus a world-space radiance cache for further bounces. You do not write any WGSL to use it — you swap two components and delete your shadow maps.

Hardware requirements — read before you start
  • A GPU with hardware ray query support: roughly RTX 20-series and up, RX 6000 and up, Arc A-series.
  • Vulkan or DirectX 12 backend. No macOS, no web, no mobile.
  • The bevy_solari cargo feature. It is not in the default feature set.
  • Solari is explicitly experimental and its API moves every release.

Meshes have to opt in — and meet strict rules

Solari builds a bottom-level acceleration structure per mesh and a TLAS per frame. Geometry that does not match the expected layout is silently skipped or rejected, so this is where most people stall.

RaytracingMesh3d contract
  • Vertex attributes exactly POSITION, NORMAL, UV_0, TANGENT — no UV_1, no vertex colours.
  • PrimitiveTopology::TriangleList, and Indices::U32. 16-bit indices are rejected.
  • Mesh::enable_raytracing must be true (it defaults to true).
  • The material must be MeshMaterial3d<StandardMaterial>. Custom materials are not traced.
  • RaytracingMesh3d is a separate component from Mesh3d. Keep both: the rasteriser fills the GBuffer, Solari lights it.

Real glTF files rarely satisfy that contract, so fix them up in the same WorldInstanceReady observer you already have:

Lights

Solari draws light from two sources only: DirectionalLight, and emissive meshes. There are no traced point or spot lights. To make an object glow, crank its emissive far past 1.0 — these are physical radiance values, so five- and six-figure numbers are normal.

Reference mode: the offline pathtracer

Solari ships a brute-force pathtracer for validating the realtime result. It converges over several seconds while the camera is still, and is far too slow to play in — but it is the ground truth you compare against when the realtime image looks wrong.

Denoising

Solari's raw output is noisy by design — it leans on temporal accumulation. With the dlss feature and an NVIDIA RTX card you can attach Dlss<DlssRayReconstructionFeature> to the camera, which denoises and upscales in one pass. It is strongly recommended and it also makes the whole thing considerably cheaper. Check DlssRayReconstructionSupported exists as a resource before inserting the component.

@binding(3) · custom pipeline

Writing your own raytracer in WGSL

If you want your own intersection code, your own sampling, or you are targeting hardware Solari cannot run on, drop to a compute pipeline: dispatch one thread per pixel, trace rays in WGSL, write into a storage texture, display that texture as a sprite or fullscreen quad.

Changed in 0.19 — render graph as systems

The RenderGraph node API is gone. impl ViewNode / add_render_graph_node becomes an ordinary system added to the Core3d, Core2d or RenderGraph schedule. RenderContext is now a system parameter instead of an argument, and you order passes with .before()/.after() against the actual system functions rather than against label enums.

The plugin: four registrations

A custom GPU pass always has the same shape. Extract data from the main world into the render world; build the pipeline once at startup; build a bind group each frame; record commands in the graph.

Resources on both sides of the boundary

ExtractResource copies a main-world resource into the render world each frame. The render world is wiped and rebuilt every frame, so anything the GPU needs has to be extracted or created there.

Create the target image in the main world, with the usage flags the compute pass needs. STORAGE_BINDING lets the shader write to it; TEXTURE_BINDING lets the sprite read it.

Pipeline creation

RenderStartup runs once, in the render world, with RenderDevice available. queue_compute_pipeline returns an id immediately and compiles in the background — you check for readiness later.

The shader

A minimal ray generation kernel. Note that the struct field order and the binding indices mirror the Rust side one for one — that correspondence is the entire contract between the two worlds.

Where to go from here

Add bounces by looping the trace and accumulating throughput; add a frame counter uniform to seed a PCG hash for stochastic sampling; accumulate into a second storage texture and divide by sample count for progressive refinement. For hardware-accelerated intersection instead of a brute-force loop, you need an acceleration structure — at which point Solari is already doing that work for you.

@binding(4) · data upload

Pushing data to buffers

Bevy gives you four routes from CPU memory to a GPU binding, at descending levels of abstraction. Pick the highest one that fits — each step down costs you render-world boilerplate.

RouteReach for it whenLives in
AsBindGroup derivePer-material data on meshesMain world
Assets<ShaderBuffer>Sharing a buffer between a material and a compute passMain world
UniformBuffer / StorageBuffer / BufferVecPer-frame data for a custom pipelineRender world

Changed in 0.19

ShaderStorageBuffer is now ShaderBuffer, still at bevy::render::storage. Also renamed: PipelineCacheError → ShaderCacheError.

Route 1 — AsBindGroup on a material

The derive generates the layout and the bind group. Attribute indices become @binding numbers in your shader.

Route 2 — updating a ShaderBuffer every frame

Mutating the asset re-uploads it. This is the easiest way to stream changing data to the GPU without touching the render world at all.

Route 4 — reading results back

Readback is asynchronous and costs a GPU stall plus at least one frame of latency. Use it for tooling, screenshots and offline bakes — not in your frame loop.

Alignment: the rule that breaks everything

std140 / std430 in one box
  • vec3<f32> occupies 12 bytes but aligns to 16. A vec3 followed by an f32 packs perfectly; two vec3s in a row waste 4 bytes each. Order your fields so every vec3 is trailed by a scalar.
  • In uniform buffers (std140), array elements are padded up to 16 bytes. array<f32, 64> silently becomes 1024 bytes. Use array<vec4<f32>, 16>, or a storage buffer.
  • Derive ShaderType on the Rust struct and it computes offsets for you — but it cannot check your WGSL. Field order and types must match by hand.
  • Struct sizes round up to their largest member's alignment. A struct ending in an f32 after a vec3 is 32 bytes, not 28.
Targeting the web

WebGL2 has no storage buffers at all — var<storage> will not compile, and uniform buffers are capped near 16 KB. If you need storage buffers or compute shaders in a browser you need WebGPU, which means shipping a WebGPU build and accepting narrower browser support. Bevy's own examples are published in both flavours for exactly this reason.

Resources are components now

The change with the widest blast radius is quiet: Resource is a subtrait of Component, and #[derive(Resource)] implements both. You can no longer derive both on one type, and broad queries such as Query<EntityMut> now see resource entities — filter them out with Without<IsResource> if a system suddenly reports a conflict.

Written against Bevy 0.19 (released 19 June 2026). Bevy is pre-1.0 and ships breaking changes roughly quarterly — check the migration guides and the official examples, which are the only sources that track the release you actually have. Solari in particular is experimental and changes shape every cycle.

Two spots to watch if you are on main rather than 0.19: bind group layouts are moving from RenderDevice::create_bind_group_layout to BindGroupLayoutDescriptor::new plus PipelineCache::get_bind_group_layout, and Image::new_target_texture has gained an extra argument.
