Ten mini tutorials that add up to one small game

Each tutorial stands on its own: its own goal, its own scenes, its own finished scripts, and a test you can run at the end. Read them in order and they assemble into a single working project — a menu you can ship, a level you can play, and a build you can hand to someone else.

  • 10 tutorials
  • ~4 hours end to end
  • No art assets needed
  • Every script shown in full

Project setup and conventions

Five minutes here saves confusion in every tutorial that follows. If you already have a project you'd rather use, skim the conventions and adapt the paths as you go — nothing in these tutorials depends on the project being new.

  1. Create the project

    In the Project Manager, click Create, name it pocket-platformer, and pick the Compatibility renderer. Compatibility runs everywhere including the web, and nothing in these ten tutorials needs Forward+. You can switch later in Project → Project Settings → Rendering → Renderer.

    Create three folders in the FileSystem dock — right-click res:// and choose New → Folder: autoload, game, ui.

  2. Set the window size and stretch

    Open Project → Project Settings → Display → Window and set:

    SettingValueWhy
    Viewport Width / Height640 × 360Small design resolution, scales cleanly to 1280×720 and 1920×1080.
    Window Width / Height Override1280 × 720The window you actually get while testing.
    Stretch → Modecanvas_itemsScales the whole UI and 2D world with the window.
    Stretch → AspectexpandWider screens see more world instead of black bars.

    New Godot 4.7 projects already start with canvas_items and expand, so you may only need to change the sizes. Turn on Advanced Settings (top-right toggle in Project Settings) if you can't see the stretch options.

  3. Know how to read the panels in this page

    Scene trees are written the way the Scene dock shows them — node name first, node type after the colon, indentation for children:

    To build that: add a Control, rename it MainMenu, add a MarginContainer as its child, rename it Margin, and so on. Node types are colour-coded the same way the editor colours its icons — green for UI nodes, blue for 2D nodes, violet for plain nodes and layers.

    Code panels always name the file they belong to. When a panel says replace the whole file, it is the complete script; when it says add to, paste it at the end of what you already have.

  4. Adopt two naming habits

    Unique names for nodes you touch from code. Right-click a node and choose Access as Unique Name (or press Ctrl+Shift+A — Cmd on macOS). The node gets a % badge, and you can reach it as %PlayButton from anywhere in that scene, no matter how you rearrange the containers later. Every %Name you see in this page assumes you did this.

    Typed variables everywhere. var speed: float = 180.0 rather than var speed = 180.0. GDScript catches more mistakes before you run, and the editor autocompletes properly.

    ShortcutDrag a node from the Scene dock into the script editor while holding Ctrl and Godot writes the @onready line for you, unique name included.

  5. Know where the autoloads are heading

    Five scripts end up in Project → Project Settings → Globals → Autoload. You'll add them one at a time, but the order matters because autoloads are readied top to bottom, and a few read each other at startup. This is the order you want by the end — drag rows in the Autoload list to fix the order at any point.

    #NameScriptAdded in
    1Eventsres://autoload/events.gdTutorial 06
    2Settingsres://autoload/settings.gdTutorial 02
    3SceneLoaderres://autoload/scene_loader.gdTutorial 03
    4Audiores://autoload/audio.gdTutorial 09
    5Gameres://autoload/game.gdTutorial 06

    The Name column is what you type in code. Settings.master_volume works from any script in the project because the autoload name becomes a global.

TUTORIAL 01

Main menu, play scene, and a pause menu that gets you home

Three scenes and two scripts. Press Play and you're in the level; press Esc and the world freezes behind a pause menu; choose Quit to menu and you're back at the title with the game running normally again.

Builds on
Nothing. This is the foundation every other tutorial attaches to.
You'll create
ui/main_menu.tscn, ui/pause_menu.tscn, game/level_01.tscn, and one input action
Key ideas
Containers for layout, SceneTree.paused, process modes, why a pause menu belongs on a CanvasLayer
Time
About 25 minutes

  1. Build the main menu scene

    Scene → New Scene → Other Node → Control. Rename the root to MainMenu and save it as res://ui/main_menu.tscn.

    Now the four settings that make it look deliberate instead of piled into a corner:

    • MainMenu → toolbar Layout → Anchors Preset → Full Rect. The root now always fills the window.
    • Layout → same Full Rect preset, then in the Inspector open Theme Overrides → Constants and set all four margins to 48.
    • Menu → Inspector: Alignment = Center, Theme Overrides → Constants → Separation = 10, Layout → Container Sizing → Horizontal = Shrink Center, and Custom Minimum Size x = 220.
    • Title → Text Pocket Platformer, Horizontal Alignment = Center, and under Theme Overrides → Font Sizes set Font Size to 32.

    Set the three buttons' text to Play, Options and Quit. Tick Disabled on OptionsButton — there's nothing behind it until Tutorial 02, and a button that does nothing is worse than a button that says it isn't ready.

    Finally, select PlayButton, OptionsButton and QuitButton and turn on Access as Unique Name for each (right-click → the option with the % symbol). That's what lets the script find them as %PlayButton.

    Why containersA VBoxContainer owns the position and size of its children — that's why you set Container Sizing on the box instead of dragging buttons around. Fight it and the layout snaps back the moment the window resizes. Tutorial 07 shows the one property in 4.7 that lets you animate a child anyway.

  2. Write the menu script

    Select the MainMenu root, click the script icon above the Scene dock, and save the new script as res://ui/main_menu.gd. Replace the template with this.

    Connecting in code or in the editor?Both work. Connecting in _ready() keeps every wire in one place you can read top to bottom, and renaming a handler won't silently break a connection stored in the .tscn. If you prefer the Node dock's signal list, use it consistently — mixing the two is how you end up with a handler that runs twice.

  3. Make the empty level

    Scene → New Scene → 2D Scene. Rename the root Level and save it as res://game/level_01.tscn.

    Give Background the Full Rect preset and a colour you can tell apart from the menu — something like #20262e. Set Hint's text to Nothing here yet. Press Esc., Full Rect preset, Horizontal and Vertical Alignment both Center.

    That Label is a placeholder with a job: it proves the scene switched. Tutorial 04 deletes it and drops a player in its place.

  4. Add the pause action

    Open Project → Project Settings → Input Map. Type pause in the box and click Add. Then click the + on the new row and press Esc. Click + again, choose Joypad Button and pick Start.

    Esc is already taken — sort ofGodot's built-in ui_cancel action is also bound to Esc, and both actions will fire. That's fine here, and it's why the pause menu below marks the event as handled: so ui_cancel doesn't also close a focused dialog behind it. Always define your own gameplay actions rather than reusing the ui_* ones — those belong to Godot's UI navigation and you'll want to rebind yours in Tutorial 05.

  5. Build the pause menu scene

    Scene → New Scene → Other Node → CanvasLayer. Rename it PauseMenu, save as res://ui/pause_menu.tscn.

    • PauseMenu → Inspector Layer = 10. Tutorial 07 puts the HUD on layer 5, so the pause menu covers it.
    • PauseMenu → Inspector Node → Process → Mode = Always. This is the load-bearing setting; the next step explains why.
    • Screen, Dim → Full Rect preset. Give Dim a colour with alpha, like black at 55%, and set its Mouse Filter to Ignore so it never swallows a click meant for a button.
    • Menu → same settings as the main menu's: Alignment Center, Separation 10, Container Sizing Horizontal Shrink Center, Custom Minimum Size x 220.
    • Title → text Paused, centered, font size 28. Buttons: Resume, Options (tick Disabled again), Quit to menu.
    • Turn on Access as Unique Name for the three buttons.
    Unique names are per-sceneThis scene has an %OptionsButton and so does the main menu. They never collide, because % resolves inside the scene that declared it — even when this scene is instanced inside another one.

  6. Write the pause script

    Attach a script to the PauseMenu root, save it as res://ui/pause_menu.gd.

    Three decisions in that file are worth understanding, because they're the ones people get wrong:

    Process Mode = Always. Setting get_tree().paused = true stops _process, _physics_process and input on every node whose process mode resolves to Inherit or Stop. A pause menu set to When Paused can close itself but can never open itself, because it isn't running when the game is live. Always means this branch runs in both states — and since children inherit, every button inside stays clickable while the world behind them is frozen.

    _unhandled_input, not _input. Input reaches _input before the UI sees it, so a player typing in a text box would trigger a pause. _unhandled_input only fires for events no Control consumed, which is what you want for a global hotkey.

    visible, not hide(). CanvasLayer is a plain Node, not a CanvasItem, so it has a visible property but no show() or hide() methods.

    Why a CanvasLayer at allControls inside a CanvasLayer ignore the game camera entirely — they don't scroll, zoom or rotate with it, and they draw above everything on lower layers. Put your pause menu directly in the level as a plain Control and it will slide off-screen the first time the camera moves.

  7. Put the pause menu in the level

    Open level_01.tscn, select the Level root, and click the chain-link icon above the Scene dock (Instantiate Child Scene). Choose pause_menu.tscn.

    Every level gets its own copy. That's deliberate: the pause menu belongs to gameplay, so it can't accidentally appear over the main menu, and you can see it in the Scene dock while you work instead of hunting through globals. Tutorial 07 adds the HUD the same way.

    The alternativeSome projects make the pause menu an autoload so it exists exactly once. That works too, but then it has to decide for itself whether the current scene is a level or a menu. Copies-per-level is the simpler default; switch later if you end up with dozens of levels.

  8. Set the main scene and run

    Press F5. Godot asks which scene to run first — pick main_menu.tscn. (You can change it later in Project Settings → Application → Run → Main Scene.)

    If Play does nothingchange_scene_to_file() is deferred: Godot swaps scenes at the end of the current frame, not on the line you call it. So a line after it still runs against the old scene. If the screen doesn't change at all, the path string is wrong — check the Output panel for Cannot open file, and copy paths with right-click → Copy Path in the FileSystem dock rather than typing them.

Check it works

  1. The menu is centered and Play has a focus ring the moment the game starts.
  2. Play lands you on the dark level with the placeholder label.
  3. Esc dims the screen and shows Paused with Resume focused; Esc again closes it.
  4. Quit to menu returns to the title — and Play still works from there. If the menu appears but is frozen and unclickable, you removed the get_tree().paused = false line.

TUTORIAL 02

An options menu that remembers

Three volume sliders and a fullscreen toggle, written to disk and re-applied on the next launch. One scene serves both menus: it opens as an overlay from the title screen and from the pause menu, with identical behaviour in each.

Builds on
Tutorial 01's two menu scenes. Standalone? Build it as its own scene and call open() from any button you like.
You'll create
Two audio buses, the Settings autoload, ui/options_menu.tscn
Key ideas
ConfigFile, user://, audio buses, DisplayServer window modes, Callable.bind()
Time
About 30 minutes

  1. Create the audio buses

    Open the Audio tab in the bottom panel. You already have Master. Click Add Bus twice and rename the new ones Music and SFX — double-click the name to edit it. Leave both routed to Master.

    A bus is a volume knob that many sounds share. Everything you play on the Music bus is controlled by one slider, and Master sits above all of them, so the master slider scales the lot.

    Where the layout livesGodot writes the buses to res://default_bus_layout.tres automatically. It will appear in your FileSystem dock — commit it, it's part of the project. Names are case-sensitive: SFX is not Sfx.

  2. Write the Settings autoload

    Right-click res://autoload → Create New → Script, name it settings.gd, and make it extend Node.

    Register it: Project → Project Settings → Globals → Autoload, pick res://autoload/settings.gd, set the Node Name to Settings, and click Add. Any script in the project can now say Settings.save().

    Why sliders are linear but volume is decibelsHuman hearing is roughly logarithmic, so audio buses are measured in dB, where 0 is full volume and -80 is effectively silence. A slider that ran from -80 to 0 would feel wrong — the whole bottom half would sound the same. So the slider stays 0–1 and linear_to_db() converts. Godot 4.4 added AudioServer.set_bus_volume_linear() if you'd rather skip the conversion; the mute check above is still worth keeping.
    Where user:// actually isRun the game and check the Output panel after adding print(OS.get_user_data_dir()) — it's under %APPDATA% on Windows, ~/Library/Application Support on macOS, ~/.local/share on Linux, and browser storage on the web. Never write to res:// at runtime: it's read-only once you export.

  3. Build the options scene

    New Scene → Other Node → Control, rename OptionsMenu, save as res://ui/options_menu.tscn.

    Settings that matter:

    • OptionsMenu, Backdrop, Center → Full Rect preset. Backdrop gets black at ~70% alpha and Mouse Filter = Stop, so clicks can't reach the menu underneath.
    • Margin → all four margin constants 20. Rows → Separation 10, Custom Minimum Size x = 360.
    • Each row's Name label: Master, Music, Effects, Fullscreen, with Custom Minimum Size x = 110.
    • Each HSlider: Layout → Container Sizing → Horizontal = Fill, Expand. Leave min/max alone — the script sets them, so the scene and the code can't drift apart.
    • Title text Options, font size 24. BackButton text Back.
    • Access as Unique Name on: MasterSlider, MusicSlider, SfxSlider, FullscreenCheck, BackButton. Tutorial 05 adds two more to that list.

  4. Write the options script

    class_name OptionsMenu registers the script as a type, so other scripts can declare var menu: OptionsMenu and get autocomplete on open() and closed.

    Apply immediately, save on exitEvery slider change is applied the moment it moves, so the player hears the result — but the file is only written in close(). Dragging a slider fires value_changed dozens of times a second; writing to disk on each one is wasted work.

  5. Hang it off the main menu

    Open main_menu.tscn, select the MainMenu root, and instance options_menu.tscn as a child (chain-link icon). Drag it below Layout so it draws on top, then turn on Access as Unique Name for it.

    Select OptionsButton and un-tick Disabled. Then make three edits to main_menu.gd:

  6. Hang it off the pause menu too

    Open pause_menu.tscn. Instance options_menu.tscn as a child of the PauseMenu root — a sibling of Screen, listed after it. Mark it as a unique name and un-tick Disabled on this scene's OptionsButton.

    The edits to pause_menu.gd are the same shape:

    Two Esc handlers, no conflictBoth the pause menu and the options overlay listen for Esc. Unhandled input travels up the tree from the deepest node, and the options overlay is deeper, so it gets first refusal. When it's open it calls set_input_as_handled() and the pause menu never hears the key; when it's hidden the visible check lets the event pass straight through. That's the whole mechanism behind layered menus — no state machine required.
    The overlay works while paused for one reasonIt inherits Process Mode = Always from the PauseMenu root you configured in Tutorial 01. If you ever move the options overlay somewhere that isn't Always, its sliders will freeze the moment the game pauses.

Check it works

  1. From the title screen, Options opens the panel and Back returns focus to the Options button.
  2. Pause in the level, open Options, and press Esc — the overlay closes but the pause menu stays open.
  3. Toggle Fullscreen; the window changes immediately.
  4. Move a slider, quit the game entirely, relaunch, reopen Options — the slider is where you left it. If it isn't, check the Output panel for the Could not write error.
  5. In the FileSystem dock's search box, nothing changes — settings.cfg lives outside the project. Open the path OS.get_user_data_dir() prints if you want to see it.

TUTORIAL 03

Scene transitions and a loading screen

One autoload replaces every change_scene_to_file() call in the project. Scenes fade out, load on a background thread with a real progress bar, and fade back in — and a scene that fails to load says so instead of freezing.

Builds on
Tutorial 01's menu and level. Standalone? The autoload is one self-contained file; call SceneLoader.change_scene(path) from anywhere.
You'll create
The SceneLoader autoload; edits to both menu scripts
Key ideas
Threaded loading, await in GDScript, Tween, building UI in code
Time
About 25 minutes

  1. Understand what's wrong with the direct call

    get_tree().change_scene_to_file() loads the scene on the main thread. For the tiny scenes you have now that's a few milliseconds and nobody notices. Put a level with a hundred sprites, a tileset and three music tracks behind it and the game stops responding — no frames, no animation, no way to tell the player anything — until it's done.

    The fix has three parts: ask for the scene on a background thread, poll how far along it is, and cover the seam with a fade so there's never a single frame of nothing.

  2. Write the loader

    Create res://autoload/scene_loader.gd. It extends CanvasLayer and builds its own interface, so there's no scene file to keep in sync.

    Register it as an autoload named SceneLoader, exactly as you did with Settings.

    Reading the flowThree awaits do the heavy lifting. await _fade_to(1.0) suspends change_scene() until the tween reports finished, then resumes on the next line — the function looks sequential but never blocks a frame. await get_tree().process_frame is the idiom for "let one frame pass", which is how you wait for a freshly swapped scene to finish entering the tree.
    Progress is not a smooth lineload_threaded_get_status() reports progress per sub-resource, so a scene with one big dependency can sit at 0 and then jump to 1. That's expected. A progress bar is honest about something is happening, not about how many seconds remain.

  3. Route the menus through it

    Two one-line swaps. In main_menu.gd:

    And in pause_menu.gd — note that the explicit unpause is gone, because change_scene() clears it for you:

    Calling close() first hides the pause menu so it isn't sitting on screen during the fade. From here on, every scene change in the project goes through SceneLoader; a stray change_scene_to_file() will skip the fade and look like a bug.

  4. Prove it with a slow scene

    Right now everything loads instantly, so you're only seeing the fade. To watch the progress bar move, temporarily add a heavy dependency to level_01.tscn — a few hundred instanced nodes, or a large imported image — and run again. Remember to take it back out.

    Check it on the web tooBrowsers are where loading time becomes visible: files arrive over the network. Threaded loading still works there, but if you export without thread support the request completes on the main thread, so progress jumps straight to 1.0. The fade keeps it looking intentional either way.

Check it works

  1. Play fades to black, shows Loading briefly, then fades into the level.
  2. Pause and Quit to menu fades back to the title, and the title screen is interactive — not frozen.
  3. Temporarily change LEVEL_PATH to a path that doesn't exist. The Output panel prints SceneLoader: no such scene and the game carries on instead of hanging. Put the path back.
  4. Click Play twice in quick succession — only one transition runs.

TUTORIAL 04

A player controller, and an input map worth rebinding

Fill the empty level with ground, two platforms and a character that runs and jumps — with coyote time and a jump buffer, because a jump that eats your input feels broken even when the physics are right.

Builds on
Tutorial 01's level_01.tscn. Standalone? Everything here lives in two scenes and one script.
You'll create
Three input actions, game/player.tscn, game/player.gd, and real geometry in the level
Key ideas
CharacterBody2D, _physics_process, get_gravity(), Input.get_axis(), named actions instead of raw keys
Time
About 30 minutes

  1. Name the actions before you write any movement

    Open Project Settings → Input Map and add three actions alongside the pause action from Tutorial 01.

    ActionKeyboardGamepad
    move_leftA, Left arrowLeft Stick Left, D-pad Left
    move_rightD, Right arrowLeft Stick Right, D-pad Right
    jumpSpace, W, Up arrowBottom Action Button (A / Cross)

    Click + on a row, then either press the key or pick Joypad Axis / Joypad Button from the dropdown. For stick axes, leave the Deadzone at 0.2 — below that, a worn thumbstick will walk your character across the room while you're not touching it.

    Why not just read the key?Input.is_key_pressed(KEY_A) works and costs you three things: gamepads, the rebinding screen in Tutorial 05, and anyone whose keyboard layout puts A somewhere else. Named actions are the indirection that makes all three possible later, for no extra effort now.

  2. Build the player scene

    New Scene → Other Node → CharacterBody2D. Rename it Player, save as res://game/player.tscn.

    • Sprite2D → drag res://icon.svg (every new project has it) into the Texture slot. Set Transform → Scale to 0.25, 0.25. You now have a 32×32 placeholder that costs nothing to replace later.
    • CollisionShape2D → in Shape, choose New CapsuleShape2D. Click the shape to expand it and set Radius 10, Height 32. A capsule slides over small ledges instead of catching on them the way a rectangle does.
    • Camera2D → leave the defaults. It follows the player because it's a child of the player.

  3. Write the movement script

    Attach a script to Player, save as res://game/player.gd.

    Four things in there are the difference between "it moves" and "it feels right":

    • Jump height, not jump velocity. You can picture 64 pixels. You cannot picture -354 pixels per second, and it changes every time you touch gravity.
    • Coyote time. For 0.12 s after leaving a ledge the jump still fires. Players read this as responsiveness; without it they read the game as dropping inputs.
    • Jump buffer. A press up to 0.12 s before landing is remembered and fires on touchdown.
    • move_toward instead of assignment. Setting velocity.x directly gives you a character that stops dead. Accelerating toward the target gives weight, and one number tunes it.
    _physics_process, not _processAnything that moves a physics body belongs in _physics_process, which runs at a fixed rate (60 Hz by default) no matter the frame rate. Input.is_action_just_pressed() is safe to read there — Godot holds "just pressed" for the whole physics tick.
    Tuning without restartingEvery @export shows up in the Inspector. Run the game, switch to the Remote tab of the Scene dock, select the live Player and drag Speed — you feel the change immediately. Values set there are discarded on stop, so write the ones you like back into the Local tab.

  4. Give the level something to stand on

    Open level_01.tscn and delete the Hint label — it has done its job. Build three static bodies and drop the player in.

    Build Ground once, then select it and press Ctrl+D twice to duplicate it for the platforms. Numbers for a 640×360 viewport:

    BodyBody positionRectangle shape sizeVisual sizeVisual position
    Ground320, 330640, 60640, 60-320, -30
    PlatformLeft170, 250160, 24160, 24-80, -12
    PlatformRight470, 180160, 24160, 24-80, -12

    Place the Player instance at 120, 260. Give each Visual a colour a shade lighter than the background so you can see the edges.

    Why the visuals need negative positionsA CollisionShape2D is centred on its node. A ColorRect — like every Control — grows right and down from its top-left corner. Offsetting the rect by half its size in each direction lines the two up. Once you're using real sprites this disappears, since Sprite2D is centred by default.
    New in 4.7CollisionShape2D gained one_way_collision_direction. Turn on One Way Collision on a platform's shape and you can now point the passable direction anywhere, instead of rotating the shape until local-up happened to face the right way. Perfect for jump-through platforms.

  5. Run it and tune

    Press F5, click Play, and move with A/D or the arrows. If the character sinks through the floor, the collision shape has no Shape resource assigned. If it jitters against a wall, its capsule is probably wider than you think — turn on Debug → Visible Collision Shapes and look.

    Start tuning with Jump Height and Speed. If jumps feel floaty, raise the project's gravity (Project Settings → Physics → 2D → Default Gravity, default 980) — the script recalculates the jump velocity from it automatically, so your jump stays 64 pixels tall while getting snappier.

Check it works

  1. The player lands on the ground and stops, rather than sinking or bouncing.
  2. Holding a direction accelerates; letting go slides to a stop over a few frames.
  3. Walk off the edge of a platform and press jump a hair too late — it still jumps. That's coyote time.
  4. Press jump just before landing — the jump fires on touchdown. That's the buffer.
  5. A gamepad moves and jumps without any extra code, and Esc still pauses everything.

What this feeds

TUTORIAL 05

Letting players rebind the controls

A row per action inside the options screen. Click it, press a key, and the binding changes for the rest of the session and every session after — including the pause key itself, with no extra wiring.

Builds on
Tutorial 02's options menu and Settings, Tutorial 04's actions. Standalone? The row scene works against any InputMap action.
You'll create
ui/key_row.tscn, ui/key_row.gd, plus a controls block in the options menu
Key ideas
InputMap at runtime, physical vs. label keycodes, storing an InputEvent as plain data
Time
About 30 minutes

  1. Decide what actually gets stored

    You cannot drop an InputEvent into a config file and expect to read it back — it's an object, and the file wants plain values. So convert it: a keyboard binding becomes {"kind": "key", "code": 65}, and rebuilding the event on load is three lines.

    The number stored is the physical keycode — the position of the key on the board, not the letter printed on it. Bind "jump" to the key left of S on a QWERTY board and it stays left of S on AZERTY, where that key is labelled Q. The label is only used for display.

    Then call it at startup — add one line to apply_all():

    Why as instead of isevent as InputEventKey returns the event typed, or null if it's the wrong class. Checking the result gives you a properly typed local variable, so the editor autocompletes physical_keycode and catches typos — which a plain if event is … block doesn't do for you.

  2. Build the row scene

    New Scene → Other Node → HBoxContainer, rename KeyRow, save as res://ui/key_row.tscn.

    ActionName → Custom Minimum Size x = 110. KeyButton → Container Sizing Horizontal = Fill, Expand. Mark both as unique names.

    That last call looks like a detour, and it is a deliberate one: the event handed to rebind() is rebuilt from the same dictionary that gets written to disk. Store one thing, apply another, and you get the bug where a binding works until you restart.

    Three details that biterelease_focus() before listening, or the focused button will treat Space as "press me again". _input rather than _unhandled_input, because you want the key before the UI turns it into navigation. And is_echo(), or holding a key fires the rebind repeatedly.

  3. Add the controls block to the options menu

    Open options_menu.tscn and add three nodes to Rows, above BackButton:

    ControlsTitle text Controls. Controls gets Separation 6 and stays empty — the script fills it. ResetButton text Reset to defaults. Mark Controls and ResetButton as unique names.

    The ordering rule@onready variables are assigned when the node enters the tree. Call a method that uses them on a freshly instantiated node and you get Invalid access to property or key on a base object of type Nil. Always add_child() first.

  4. Run it, then quit and run it again

    Open Options from either menu. Click the button next to Jump, press J, and jump with J. Press Esc while a row is waiting and it cancels without changing anything.

    Rebind Pause to P and close the options screen. P now pauses the game and Esc doesn't — and you didn't touch pause_menu.gd. That's the whole payoff of naming actions in Tutorial 04.

    Two things this version deliberately leaves out

    Conflict detection. Nothing stops the player binding Jump and Move right to the same key. To catch it, loop Settings.REBINDABLE before calling rebind(), compare InputMap.action_get_events() entries against the new keycode, and either refuse or clear the other action first.

    Gamepad rebinding. The row ignores InputEventJoypadButton. To accept it, widen the filter in _input(), add a "joy_button" case to the two converter functions, and give Settings a matching _erase_joypad_events(). Keep the two kinds in separate storage slots so binding a key never removes a pad button.

Check it works

  1. Each row shows the current key, spelled the way your keyboard layout spells it.
  2. Rebinding takes effect immediately, without leaving the options screen.
  3. Reset to defaults puts every row back to what Project Settings declares.
  4. Quit the game completely, relaunch, and your bindings are still there — that's apply_bindings() running from apply_all().
  5. A gamepad still moves and jumps after you rebind the keyboard.

Signals, and the event bus that keeps scenes apart

  1. Know which of the two tools you need

    Godot gives you two ways to let one node tell another something happened, and picking the wrong one is the most common way a small project turns into an unreadable one.

    Use a direct signalUse the event bus

TUTORIAL 07

A HUD that reacts to the game instead of polling it

Hearts and a coin counter that update from signals, a red flash when you take a hit, and a coin total that pops — inside a container, which until Godot 4.7 was the one thing you couldn't animate.

Builds on
Tutorial 06's Events and Game. Standalone? Point the two signal connections at whatever your project already emits.
You'll create
ui/hud.tscn and ui/hud.gd
Key ideas
Anchors vs containers, building repeated UI in code, Tween chains, offset_transform_*
Time
About 25 minutes

  1. Build the HUD scene

    New Scene → Other Node → CanvasLayer, rename HUD, save as res://ui/hud.tscn. Set its Layer to 5 — above the world, below the pause menu's layer 10.

    • Flash → Full Rect, colour a strong red with alpha 0, Mouse Filter = Ignore. It's invisible until something hits you.
    • Root → Full Rect, all four margin constants 16.
    • Top → Container Sizing → Vertical = Shrink Begin, so the bar hugs the top of the screen instead of stretching down it.
    • Hearts → Separation 4. Leave it empty; the script fills it.
    • CoinBox → Container Sizing → Horizontal = Fill, Expand and Alignment = End. That single expand flag is what pushes the coin counter to the right edge.
    • CoinIcon → texture res://icon.svg, Custom Minimum Size 20, 20, Expand Mode = Ignore Size, Stretch Mode = Keep Aspect Centered. CoinLabel → text 0.
    • Unique names on Flash, Hearts, CoinBox and CoinLabel.
    Anchors or containers?Anchors pin one control to an edge. Containers arrange several and own their children's geometry. This HUD uses both, in the right places: anchors put the bar across the top, containers space the hearts and shove the coin group right. Reach for anchors first when a thing is alone on the screen, containers as soon as there are two of them in a row.

  2. Write the HUD script

    Note what the HUD doesn't do: it never looks for the player, never reads Game.health, and never runs code every frame. It sits idle until a signal arrives. That's also why it survives the player being deleted and rebuilt on every respawn.

    New in 4.7 — why the pop works at allA Container sets its children's position, rotation and scale every time it re-sorts. Scale a child the old way and the next layout pass silently resets it, which is why pre-4.7 projects wrap animated UI in an extra Control. offset_transform_* is a second transform applied after layout, so the container never fights it. Because offset_transform_visual_only defaults to true, a button that scales up doesn't drag its click area with it and can't lose the mouse mid-hover.
    Tween chains run in orderTwo tween_property() calls on the same tween play one after the other by default. Want them together? Call tween.set_parallel(true) first. kill() on the old tween before starting a new one is the standard guard against two animations writing to the same property.

  3. Put it in the level

    Open level_01.tscn and instance hud.tscn as a child of Level, next to the pause menu.

    Ready order, and why broadcast() lands correctlyGodot calls _ready() on children before parents. The HUD is a child of the level, so it connects its signals and asks for a broadcast first; the level's own _ready() then calls Game.start_new_run(), which broadcasts again with fresh values. The HUD is already listening, so it shows three hearts and zero coins. Depth-first, bottom-up — worth committing to memory.

Check it works

  1. Three hearts top-left, coin counter top-right, and both stay put when you resize the window.
  2. Collecting a coin bumps the number and the group springs back to size.
  3. Falling into the killzone dims a heart and flashes the screen red.
  4. Pausing draws the pause menu over the HUD. If it's underneath, the layer numbers are the wrong way round.
  5. After a death and reload, the hearts are full again with no extra code — the rebuilt HUD asks for a broadcast on the way in.

What this feeds

TUTORIAL 10

Exporting a build someone else can run

Turn the project into a Windows executable, a Linux binary and a web build — and find the handful of things that work in the editor and quietly don't in a build, before a player finds them for you.

Builds on
Anything. Do this once early and again before you share; the first export of a project is always the one with surprises.
You'll create
Export presets, an export/ folder, and a build you can hand to someone
Key ideas
Export templates, presets, feature tags, debug vs release, where user:// goes
Time
About 30 minutes, most of it downloading

  1. Get the export templates

    The editor can't build for a platform until it has that platform's template — a pre-built copy of the engine your game's data is attached to. Open Editor → Manage Export Templates and download.

    New in 4.7The template downloader can fetch individual platforms, and even individual architectures, instead of the old all-or-nothing package. If you only ship Windows and web, you no longer pay for every console-less platform in the set. The templates must match your editor version exactly — 4.7.2 templates for a 4.7.2 editor — so expect to download again after every engine update.

  2. Create the presets

    Open Project → Export and click Add once per platform. For each one set an Export Path inside a new export/ folder next to your project — not inside res://, or the next export will try to package the previous one.

    PresetExport pathWorth setting
    Windows Desktopexport/windows/pocket-platformer.exeLeave Embed PCK on for a single file. Console Wrapper produces a second .console.exe that shows print() output — keep it while testing.
    Linuxexport/linux/pocket-platformer.x86_64Mark the result executable (chmod +x) if you move it between machines.
    Webexport/web/index.htmlExport into an empty folder: it writes six or seven files that all belong together.

    In each preset's Resources tab, leave the mode on Export all resources in the project. Your audio autoload builds paths as strings and calls load() at runtime, and nothing in any scene points at those files — under the "export selected scenes" mode they'd be stripped out and every sound would go missing in the build only.

    The class of bug this createsAnything loaded by a string you assembled at runtime is invisible to the exporter's dependency scan. If you ever narrow the resource mode, add those paths to Filters to export non-resource files or keep a scene that references them.

  3. Export, then run the build and not the editor

    Click Export Project, untick Export With Debug for anything you're giving to a player, and run the result from your file manager. Three things behave differently outside the editor, and this project already deals with two of them:

    In the editorIn a build
    res:// is a folder you can write to.res:// is packed and read-only. Anything written at runtime must go to user:// — which is why settings.cfg and save_01.json live there.
    print() appears in the Output panel.It goes to a terminal. On Windows that means running the .console.exe; otherwise you see nothing.
    File paths are case-insensitive on Windows and macOS.Exported packs are always case-sensitive. res://Audio/Coin.wav will fail in a build even though it worked while you were developing.

    Check the things this project actually does: change a volume slider, quit, relaunch the build, and confirm it stuck. Play, quit to menu, relaunch — Continue should be live.

  4. Know where the player's files land

    After export, user:// resolves to app_userdata/<project name> under the platform's data directory — %APPDATA%\Godot, ~/Library/Application Support/Godot, or ~/.local/share/godot. Two consequences worth knowing before you ship:

    • Renaming the project in Project Settings moves the folder, and every existing player's saves stop being found. Set Application → Config → Use Custom User Dir and a fixed Custom User Dir Name once, early, and the name is yours regardless of what the project is called.
    • On the web, user:// is backed by browser storage. It survives reloads but not a cleared cache, and it's per-origin — the same build on two domains has two separate save files.

  5. Handle the web build's quirks

    Don't open the exported index.html by double-clicking it: browsers refuse to load the engine from a file:// URL. Use Remote Debug → Run in Browser in the editor, which serves it locally with the headers the engine needs.

    Those headers are the web build's main deployment problem. Threaded builds require cross-origin isolation (Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy), which many static hosts don't send. itch.io has a SharedArrayBuffer support checkbox on the project page that turns them on. GitHub Pages does not, so either host elsewhere or export with thread support off.

    This is also where the OS.has_feature("web") check from Tutorial 01 pays for itself: get_tree().quit() cannot close a browser tab, so the Quit button hides itself rather than sitting there doing nothing.

    Other feature tags worth knowing

    OS.has_feature("editor") is true in the editor and false in any export — use it to guard developer shortcuts. OS.has_feature("debug") distinguishes a debug export from a release one. "mobile", "pc", "windows", "linux", "macos", "android", "ios" and "web" do what you'd expect. You can also define your own in a preset's Features tab, which is the tidy way to build a demo version from the same project.

  6. Tell git what to ignore

    Two folders should never be committed: Godot's own cache, and your builds.

    Everything else — .tscn, .tres, .gd, project.godot, default_bus_layout.tres, and the .import files next to your assets — is source and belongs in the repository. The .import files in particular: without them, a fresh clone re-imports every asset with new IDs and your scenes lose their textures.

Release checklist

  1. Templates match the editor version exactly.
  2. Export With Debug is off for the build you distribute.
  3. The build runs from a folder that isn't your project, on a machine without Godot if you can manage it.
  4. Settings and saves persist across a relaunch of the build.
  5. Sound plays. A missing audio file is invisible in the editor if the file is there and packed if it isn't.
  6. The window opens at a sensible size and the UI still lays out correctly when it's resized or fullscreened.
  7. Quitting works — and on the web, the Quit button is gone.

Done

That's a complete loop: title screen, options that persist, a level you can play, a HUD, a save, sound, and a build. The reference below is what the finished project looks like from above.
