Where does this data live?

Storing app and game state in Bevya decision reference, not a tutorial

Every piece of data in a Bevy app has to land somewhere: on an entity, in a resource, in the asset system, in a message queue, or inside a single system. Picking wrong is the single most common cause of refactors at month three. This sheet gives you the decision rule first, then the API, then worked layouts for six real kinds of app.

01

The router

Read top to bottom and stop at the first row that matches your data. The rows are ordered by how strongly they decide the answer — the first three settle roughly 80% of real cases.

Start with cardinality, not with the data

first match wins
Is there more than one of this thing in the world at once? Enemies, chunks, bullets, UI nodes, selected vertices, inventory slots.
Component on an entity
Is there exactly one, forever, and it isn't attached to anything in the world? Score, gravity constant, key bindings, the tick counter, the active tool.
Resource
Is it big, shared by many entities, and loaded or generated rather than simulated? Meshes, textures, audio, block definition tables, weapon stat sheets.
Asset + Handle<T>
Is it a thing that happened, that several systems want to know about later this frame? Damage dealt, block broken, file opened, collision started.
Message
Is it a thing that happened that needs handling right now, before the next system runs? Death cleanup, "entity spawned, wire up its children", UI button pressed.
Event + observer
Does the whole app behave differently depending on it, with enter/exit work at the boundary? Main menu vs playing vs paused; edit mode vs render preview; loading.
State
Does exactly one system need it, and nobody else ever reads it? Debounce timer, cached scratch buffer, "did I already log this".
Local<T>
Is it only ever meaningful together with data you already have? The y in a position, the cooldown inside a weapon, an id inside a struct.
Just a field
The one-line version

Many → component. One → resource. Heavy and shared → asset. Transient → message or event. Everything else on this page is refinement of those four.

The tie-breaker questions

When two answers both look defensible, these break the tie in the direction that ages well:

Prefer the component

Could there ever be two? Split-screen means two players. A second viewport means two cameras. Undo means two document versions. A resource that has to become plural later is a painful refactor; a component that stays singular costs you nothing but a Single<T> query.

Prefer the resource

Does every system need it, on an entity that has no other reason to exist? Don't invent a placeholder entity just to hold global config. A resource is the honest representation of "one global thing".

Prefer the asset

Would cloning it per entity hurt? Assets are refcounted and shared: 10,000 entities holding the same Handle<Mesh> store 10,000 cheap handles and one mesh. Also the only sane home for anything hot-reloadable.

Prefer the message

Are you writing a Vec into a resource and draining it next frame? That's a message queue you're rebuilding by hand. Use Message and get the double-buffering, per-reader cursors and cleanup for free.

02

The storage kinds

Nine places data can live, each with what it is, when to reach for it, and the current 0.19 API. The left edge of every code block is colour-coded to the storage kind it demonstrates.

Component — data attached to an entity

The default answer. A component is a plain struct stored in a column next to every other entity that has the same set of components. Cheap to iterate in bulk, cheap to add and remove one at a time, and queryable by combination.

component basics
#[derive(Component)]
struct Health { current: f32, max: f32 }

// Marker: zero bytes, exists purely to be queried on.
#[derive(Component)]
struct Enemy;

// Newtype over a primitive is idiomatic and free.
#[derive(Component)]
struct Damage(pub f32);

fn decay(mut q: Query<&mut Health, With<Enemy>>, time: Res<Time>) {
    for mut hp in &mut q {
        hp.current -= 1.0 * time.delta_secs();
    }
}

Required components — the replacement for bundles

Since 0.15, a component can declare what else must exist alongside it. Spawning the one component pulls in the rest, recursively. Bundles still work, but required components are the idiomatic way to express "a Player is never without Health".

required components (0.15+)
#[derive(Component)]
#[require(
    Health = Health { current: 100.0, max: 100.0 },  // explicit value
    Inventory,                                        // Default::default()
    Transform,
    Visibility,
)]
struct Player;

// One line spawns Player + Health + Inventory + Transform + Visibility,
// plus anything those require in turn (GlobalTransform, etc).
commands.spawn(Player);

// Supported forms inside #[require(..)]:
//   A                      -> Default::default()
//   B(1)                   -> tuple struct
//   C { x: 1, ..default() } -> named fields
//   D::One / E::ONE        -> variant or associated const
//   F::new(1) / G = expr   -> constructor or arbitrary expression

Storage strategy: table vs sparse set

Default is table storage: dense columns, fastest iteration, but adding or removing the component moves the entity to a different archetype (a memcpy of all its other components). Sparse set storage makes add/remove cheap and iteration slower. Choose sparse set only for components that are toggled constantly on many entities.

storage + mutability + hooks
// Toggled every frame on thousands of entities -> sparse set.
#[derive(Component)]
#[component(storage = "SparseSet")]
struct Burning;

// Immutable: can only be replaced wholesale, never mutated in place.
// Guarantees hooks/observers see every change. Good for ids and keys.
#[derive(Component)]
#[component(immutable)]
struct ChunkCoord(IVec3);

// Lifecycle hooks run inline, before any observer.
// 0.19: on_replace was renamed to on_discard.
#[derive(Component)]
#[component(on_add = index_chunk, on_remove = unindex_chunk)]
struct LoadedChunk;
Cost model worth memorising

Adding or removing a table component is an archetype move. Mutating a component's fields is nearly free. So model "state that flips often" as a field or an enum inside a component you already have, not as a marker you add and remove 60 times a second — unless you make that marker sparse set.

Resource — the singleton

A resource is data of which at most one exists. In 0.19 resources are literally components stored on a hidden singleton entity, which is why they now support hooks, observers, relationships and immutability. The everyday API is unchanged.

resource basics
#[derive(Resource)]
struct Score(u32);

#[derive(Resource, Default)]
struct WorldSettings { gravity: f32, render_distance: u32 }

app.insert_resource(Score(0))            // explicit value
   .init_resource::<WorldSettings>();      // Default or FromWorld

fn award(mut score: ResMut<Score>, settings: Res<WorldSettings>) {
    score.0 += 10;
}

// May not exist yet? Take it as an Option and handle None.
fn maybe(save: Option<Res<SaveFile>>) { if let Some(s) = save { /* .. */ } }

// FromWorld when construction needs other data (e.g. an asset handle).
impl FromWorld for BlockAtlas {
    fn from_world(world: &mut World) -> Self {
        let assets = world.resource::<AssetServer>();
        BlockAtlas { image: assets.load("blocks.png") }
    }
}
0.19 breaking change — read this before copying old code

#[derive(Resource)] now also implements Component, so a type can no longer be both a component and a resource. If you had #[derive(Component, Resource)] for a "global fallback that can be overridden per entity" pattern, split it into two types — GlobalFoo (resource) and Foo (component). Bevy did exactly this internally for its UI debug options.

Non-send data

For anything that isn't Send — raw OS handles, some GPU or audio interop, single-threaded C libraries. It's pinned to the main thread and is now called "non-send data" rather than "non-send resource".

non-send (0.19 naming)
app.insert_non_send(PlatformAudioHandle::new());
// was: insert_non_send_resource

fn poke(handle: NonSend<PlatformAudioHandle>) { /* main thread only */ }

Asset — heavy, shared, refcounted

Assets live in a central Assets<T> store; entities hold a cheap Handle<T>. Anything loaded from disk belongs here, and so does anything you generate procedurally that many entities share. Handles refcount: when the last one drops, the asset is unloaded.

custom assets + handles
// Derive Reflect (not just TypePath) if you want handles to survive
// serialization round-trips — required as of 0.19.
#[derive(Asset, Reflect)]
#[reflect(Asset)]
struct WeaponStats { damage: f32, rpm: f32, spread: f32 }

// Register it, then load or insert.
app.init_asset::<WeaponStats>();

fn setup(mut commands: Commands, mut stats: ResMut<Assets<WeaponStats>>) {
    let rifle = stats.add(WeaponStats { damage: 24.0, rpm: 600.0, spread: 0.02 });
    commands.spawn((Weapon, WeaponKind(rifle.clone())));  // cloning a handle is cheap
}

// Reading through a handle
fn fire(q: Query<&WeaponKind>, stats: Res<Assets<WeaponStats>>) {
    for kind in &q {
        let Some(s) = stats.get(&kind.0) else { continue };
        // s.damage ..
    }
}
0.19 change

Assets::get_mut returns an AssetMut<A> guard rather than &mut A, and only fires AssetEvent::Modified if you actually write. On materials that event is expensive — guard your writes with an equality check before assigning.

Message — buffered, read next

This is the big naming change. What used to be called an event (with EventWriter / EventReader) is now a Message. Messages are double-buffered: written this frame, readable this frame and next, then dropped. Each reader keeps its own cursor, so every interested system sees every message exactly once.

messages (was: buffered events)
#[derive(Message)]
struct BlockBroken { pos: IVec3, by: Entity }

app.add_message::<BlockBroken>();

fn mine(mut writer: MessageWriter<BlockBroken>) {
    writer.write(BlockBroken { pos: IVec3::ZERO, by: entity });
}

fn drop_item(mut reader: MessageReader<BlockBroken>) {
    for msg in reader.read() { /* spawn pickup */ }
}

// Old names, still seen in every pre-0.17 tutorial:
//   Event  -> Message          EventWriter -> MessageWriter
//   Events -> Messages         EventReader -> MessageReader
//   send() -> write()          add_event   -> add_message

Event + observer — immediate, targeted

Event now means only one thing: something triggered and observed. Observers run immediately when commands are applied, not on a schedule. Use them for reactions that must not be a frame late, and for anything scoped to a specific entity.

events + observers (0.17+ syntax)
// Global event: no target.
#[derive(Event)]
struct LevelLoaded;

// Entity event: the target lives in a field named `entity` by default.
#[derive(EntityEvent)]
struct Damaged { entity: Entity, amount: f32 }

commands.trigger(Damaged { entity: target, amount: 12.0 });

// Global observer: runs for every Damaged, whoever it targets.
app.add_observer(|damage: On<Damaged>, mut q: Query<&mut Health>| {
    if let Ok(mut hp) = q.get_mut(damage.entity) { hp.current -= damage.amount; }
});

// Entity-scoped observer: only for this one entity.
commands.spawn(Boss).observe(|damage: On<Damaged>| { /* boss-only reaction */ });

// Lifecycle events are just events you can observe:
// Add, Insert, Discard (was Replace), Remove, Despawn
app.add_observer(|added: On<Add, LoadedChunk>, mut index: ResMut<ChunkIndex>| {
    index.insert(added.entity);
});

// 0.19: observers accept run conditions too.
app.add_observer(on_damage.run_if(in_state(GameState::Playing)));

State — app-level modes

States drive which systems run at all, and give you enter/exit hooks. Anything with a real "mode" — menu, loading, playing, paused, edit vs preview — belongs here rather than in a bool resource, because you get scheduling and automatic cleanup for free.

states, substates, scoped entities
#[derive(States, Default, Debug, Clone, PartialEq, Eq, Hash)]
enum AppState { #[default] Loading, Menu, Playing }

// A substate only exists while its parent state matches.
#[derive(SubStates, Default, Debug, Clone, PartialEq, Eq, Hash)]
#[source(AppState = AppState::Playing)]
enum Paused { #[default] Running, Paused }

app.init_state::<AppState>()
   .add_sub_state::<Paused>()
   .add_systems(OnEnter(AppState::Playing), spawn_world)
   .add_systems(OnExit(AppState::Playing), save_world)
   .add_systems(Update, tick.run_if(in_state(Paused::Running)));

// Read and write
fn pause(state: Res<State<AppState>>, mut next: ResMut<NextState<AppState>>) {
    if *state.get() == AppState::Playing { next.set(AppState::Menu); }
}

// Entities that should die when the state ends — no manual cleanup system.
commands.spawn((Enemy, DespawnOnExit(AppState::Playing)));
0.19 detail

NextState::set() now fires transition schedules even when the target equals the current state, so DespawnOnEnter/DespawnOnExit run on a same-state transition. If you want the old behaviour, use set_if_neq().

Relationship — data that is a link

When one entity points at others, don't store a Vec<Entity> by hand. A relationship keeps both directions in sync automatically, cleans up on despawn, and can cascade despawns. ChildOf/Children is just the built-in instance of this system.

custom relationships
// The "one" side: lives on the item, points at the owner.
#[derive(Component)]
#[relationship(relationship_target = Inventory)]
struct StoredIn(Entity);

// The "many" side: lives on the owner, Bevy maintains the Vec.
#[derive(Component)]
#[relationship_target(relationship = StoredIn, linked_spawn)]
struct Inventory(Vec<Entity>);

// linked_spawn: despawning the owner despawns the contents too.

commands.spawn((Player, related!(Inventory[ Sword, Torch, Bread ])));
commands.spawn((Chest, children![ Lid, Lock ]));   // hierarchy shorthand

fn count(q: Query<&Inventory, With<Player>>) { /* .0.len() */ }

// 0.19: relationships may point at themselves if you opt in.
#[relationship(relationship_target = PeopleILike, allow_self_referential)]

Local — one system's private memory

State that belongs to a single system and would only pollute the global namespace as a resource. Persists across runs of that system, initialised with Default.

Local and system-private state
fn autosave(time: Res<Time>, mut timer: Local<Timer>, mut commands: Commands) {
    if timer.tick(time.delta()).just_finished() { /* write save */ }
}

// Also useful: a scratch buffer you don't want to reallocate every frame.
fn rebuild_mesh(mut scratch: Local<Vec<Vec3>>) {
    scratch.clear();
    // .. fill and use, allocation is reused across frames
}

Plain fields, and when a struct is enough

Not everything needs to be an ECS citizen. If two values are only meaningful together and are always read together, they're fields of one component, not two components. A component per field is a real and common mistake — it multiplies archetypes and makes every query longer without buying anything.

granularity
// Too fine: always read together, never queried separately.
#[derive(Component)] struct AmmoInMag(u32);
#[derive(Component)] struct AmmoReserve(u32);
#[derive(Component)] struct MagSize(u32);

// Right-sized.
#[derive(Component)]
struct Ammo { in_mag: u32, reserve: u32, mag_size: u32 }

// Split only when systems genuinely differ in what they touch.
// Transform and Health are separate because movement never reads health.

Scene & template data (BSN, new in 0.19)

0.19 shipped BSN, a scene notation that describes entity trees as composable, patchable data. It doesn't replace the storage decisions above — it's how you author the initial arrangement of them. Its most relevant feature here is SceneComponent, which finally guarantees "if this component exists, its whole scene exists".

bsn! and SceneComponent
// A scene is a patch: unspecified fields keep their defaults.
fn player() -> impl Scene {
    bsn! {
        Player { score: 0 }
        Children [
            Sprite { image: "player.png" },   // asset path, no AssetServer plumbing
        ]
    }
}

fn setup(mut commands: Commands) { commands.spawn_scene(player()); }

// SceneComponent ties a component to the entity tree it needs.
// Query for Player and you may assume LeftHand and RightHand children exist.
#[derive(SceneComponent, Default, Clone)]
struct Player { score: usize }

impl Player {
    fn scene() -> impl Scene {
        bsn! { Transform Children [ LeftHand, RightHand ] }
    }
}

world.spawn_scene(bsn! { @Player { score: 10 } });
03

Resource or component?

The question people actually ask. Here is the full rule, the grey areas, and the escape hatches for when the singleton turns out not to be one.

The rule

A resource is a component with a cardinality guarantee of one. That's now literally true in the engine. So the question is never "is this important enough to be global" — it's only ever how many of these exist, and does anything in the world own it.

DataGoes whereBecause
Gravity, tick rate, render distanceResourceOne per world, owned by nothing
Player healthComponentOwned by the player entity; there might be two players
Score in a single-player gameResourceOne, global, no owner
Score in a 4-player party gameComponentPer-player — this is the classic refactor
Key bindingsResourceOne config, read by everything
Which entity is selectedBoth, usuallySelected marker component + a Selection resource for order/anchor
The camera's transformComponentCameras are entities; you may add a second
The loaded voxel worldResource holding chunk lookup, chunks as entitiesIndex is one; chunks are many
Undo stackResourceOne document-wide history, not owned by any entity
Elapsed play timeResourceOne clock
Cooldown on an abilityComponentOne per ability instance
Mouse world-ray this frameResource (recomputed each frame)One derived value, many consumers

The three grey areas

Grey area 1

"There's only one player"

Until there's split-screen, a replay ghost, a spectator, or a networked second client. Player data is nearly always component data on a player entity. Use Single<&Player> to read it as conveniently as a resource, with none of the lock-in.

Grey area 2

"It's one thing, but the world owns it"

A single terrain, a single document, a single level. If systems need to attach transforms, children, or visibility to it, it wants to be an entity — those things only exist on entities. Keep a resource holding its Entity id if lookups are frequent.

Grey area 3

"It's a lookup table"

Block definitions, item stats, spell data. Resource if it's small and code-defined; asset if it's loaded from a file, hot-reloadable, or big. Assets win as soon as designers need to edit it without a recompile.

Reading a singleton entity like a resource

Single, and the resource-holding-an-Entity pattern
// Errors (skips the system) if there isn't exactly one match.
fn move_player(player: Single<&mut Transform, With<Player>>) {
    // deref straight to the Transform
}

// Tolerant version: runs even when there is no player.
fn hud(player: Option<Single<&Health, With<Player>>>) { /* .. */ }

// When you look it up constantly, cache the id in a resource.
// The entity holds the data; the resource is just a pointer.
#[derive(Resource)]
struct ActiveDocument(Entity);

fn edit(doc: Res<ActiveDocument>, mut q: Query<&mut MeshData>) {
    let Ok(mut mesh) = q.get_mut(doc.0) else { return };
}
Migration escape hatch

Turning a resource into a component later is mostly mechanical: Res<T> becomes Single<&T>, ResMut<T> becomes Single<&mut T>, and you spawn it instead of inserting it. Going the other way is easy too. What is not easy is untangling a resource that grew into a god-object holding twelve unrelated things — so split resources by who writes them, not by what they're about.

Six app shapes

Concrete data layouts for concrete projects. Each one lists the decisions that matter, the one mistake that specific genre invites, and code for the part that isn't obvious.

Voxel sandbox — a Minecraft clone

Defining problem: millions of blocks, and you cannot afford an entity for any of them. Everything follows from batching blocks into chunks.

Component
Chunk — one entity per chunk, holding ChunkCoord(IVec3) and ChunkVoxels(Box<[BlockId; 4096]>). The voxels are a flat array inside one component, not 4096 components.
Component
Dirty — sparse-set marker meaning "remesh me". Added and removed constantly, so table storage would thrash archetypes.
Component
Entities that are actually entities: players, mobs, dropped items, minecarts, block entities like chests. Anything with behaviour or per-instance state.
Resource
ChunkIndex — HashMap<IVec3, Entity>. The one lookup everything needs. Maintain it from on_add/on_remove hooks so it can never drift.
Resource
WorldGenConfig (seed, noise params), WorldSettings (render distance, simulation distance), TimeOfDay.
Asset
BlockRegistry — hardness, tool, drops, texture indices, per block type. Loaded from RON or JSON so modders and designers can edit it. Blocks in chunks store a BlockId index into it.
Asset
Generated chunk meshes — one Handle<Mesh> per chunk, replaced on remesh. Also the block atlas image.
Message
BlockChanged { pos, old, new } — read by the remesher, the lighting system, the save system, and the network layer. A textbook many-readers case.
State
AppState: MainMenu → GeneratingWorld → InGame, with Paused as a substate.
The mistake this genre invites

One entity per block. A modest 512×128×512 world is 33 million blocks; at even 50 bytes of ECS overhead each that's gigabytes before you store anything useful, and every query walks all of it. Blocks are array elements, chunks are entities. The moment a block needs real per-instance state (a chest with contents, a furnace mid-smelt), spawn a separate "block entity" that references the coordinate — that's what Minecraft itself does.

chunk storage + a self-maintaining index
const CHUNK: usize = 16;

#[derive(Component, Clone, Copy, PartialEq, Eq, Hash)]
#[component(immutable)]              // coord never changes -> hooks can't miss an update
struct ChunkCoord(IVec3);

#[derive(Component)]
struct ChunkVoxels(Box<[BlockId; CHUNK * CHUNK * CHUNK]>);

#[derive(Component)]
#[component(storage = "SparseSet")]   // toggled every frame -> avoid archetype moves
struct NeedsRemesh;

#[derive(Resource, Default)]
struct ChunkIndex(HashMap<IVec3, Entity>);

// Hooks keep the index correct without anyone remembering to update it.
fn build(app: &mut App) {
    app.init_resource::<ChunkIndex>()
       .add_observer(|add: On<Add, ChunkCoord>,
                      q: Query<&ChunkCoord>,
                      mut idx: ResMut<ChunkIndex>| {
            if let Ok(c) = q.get(add.entity) { idx.0.insert(c.0, add.entity); }
       })
       .add_observer(|rm: On<Remove, ChunkCoord>,
                      q: Query<&ChunkCoord>,
                      mut idx: ResMut<ChunkIndex>| {
            if let Ok(c) = q.get(rm.entity) { idx.0.remove(&c.0); }
       });
}

// Writing a block: mutate the array, flag the chunk, announce the change.
fn set_block(
    pos: IVec3, block: BlockId,
    idx: Res<ChunkIndex>,
    mut q: Query<&mut ChunkVoxels>,
    mut commands: Commands,
    mut changed: MessageWriter<BlockChanged>,
) {
    let chunk_pos = pos.div_euclid(IVec3::splat(CHUNK as i32));
    let Some(&e) = idx.0.get(&chunk_pos) else { return };
    let Ok(mut voxels) = q.get_mut(e) else { return };

    let i = local_index(pos);
    let old = voxels.0[i];
    voxels.0[i] = block;

    commands.entity(e).insert(NeedsRemesh);
    changed.write(BlockChanged { pos, old, new: block });
}

First-person shooter

Defining problem: fast-changing per-entity state, weapon definitions that designers tune, and a hard split between "what a weapon is" and "what this weapon instance is doing right now".

Component
Player entity: Transform, Velocity, Health, Grounded (sparse marker), LookAngles, Team. Camera is a child entity, not the same entity — you'll want to shake and recoil it independently.
Component
Weapon instance: an entity holding Ammo { in_mag, reserve }, FireTimer, Heat, plus a Handle<WeaponStats>. Related to its owner via a custom relationship (Equipped/Loadout) so despawning the player cleans up the guns.
Asset
WeaponStats — damage curve, RPM, spread, recoil pattern, reload time. Loaded from files; hot-reloadable so balance changes don't need a rebuild. Never duplicated per instance.
Resource
InputConfig (bindings, sensitivity, invert-Y), GameRules (friendly fire, round length), MatchState (score by team, round number, time left).
Message
DamageDealt { target, amount, from, hit_kind } — consumed by health, hitmarker UI, killfeed, scoring, and stats. Keeping it a message means adding the killfeed later touches nothing else.
Event
Died { entity } as an EntityEvent, so per-entity observers can do bespoke death behaviour (boss explodes, player enters spectate) without a central match statement.
State
MatchPhase: Warmup → Live → RoundEnd → Scoreboard. Enter/exit handles respawn-all and freeze-input cleanly.
The mistake this genre invites

Copying weapon stats into every weapon instance as component fields. It works right up until you want to rebalance the rifle: now the change has to touch 200 live entities and the save file. Definition data is an asset; instance data is components. Same rule for enemy archetypes, ability definitions, and vehicle handling.

definition vs instance, and damage as a message
// ---- Definition: shared, tunable, loaded from disk ----
#[derive(Asset, Reflect)]
#[reflect(Asset)]
struct WeaponStats {
    damage: f32, rpm: f32, mag_size: u32,
    reload_secs: f32, spread_deg: f32,
}

// ---- Instance: per weapon entity, changes every frame ----
#[derive(Component)]
struct WeaponInstance { stats: Handle<WeaponStats>, since_shot: f32 }

#[derive(Component)]
struct Ammo { in_mag: u32, reserve: u32 }

// ---- Ownership as a relationship, not a Vec<Entity> ----
#[derive(Component)]
#[relationship(relationship_target = Loadout)]
struct EquippedBy(Entity);

#[derive(Component)]
#[relationship_target(relationship = EquippedBy, linked_spawn)]
struct Loadout(Vec<Entity>);

// ---- One message, many independent consumers ----
#[derive(Message)]
struct DamageDealt { target: Entity, from: Entity, amount: f32, headshot: bool }

fn apply_damage(mut hits: MessageReader<DamageDealt>,
                mut q: Query<&mut Health>,
                mut commands: Commands) {
    for hit in hits.read() {
        let Ok(mut hp) = q.get_mut(hit.target) else { continue };
        hp.current -= hit.amount;
        if hp.current <= 0.0 {
            // Immediate, entity-targeted -> event, not message.
            commands.trigger(Died { entity: hit.target, by: hit.from });
        }
    }
}
// killfeed, hitmarkers, scoring and stats each read DamageDealt
// independently — none of them know the others exist.

3D modelling app / level editor

Defining problem: this isn't a game loop, it's a document. Undo, selection, tools and multiple open files are the data model, and none of them are things game tutorials cover.

Component
Object entity per scene object: Transform, Mesh3d(Handle<Mesh>), ObjectName, and a stable ObjectId(Uuid) that survives save/load (an Entity id does not).
Component
Selected — a marker, not a list in a resource. Then "highlight selected" is a query, "delete selected" is a query, and selection can never point at a despawned entity.
Component
Document root — one entity per open file, with objects as its children. Multiple documents are then free, and closing one is a single despawn.
Resource
ActiveDocument(Entity), ToolSettings (snap increment, grid size, units), ViewportPrefs (shading mode, gizmo scale), SelectionAnchor (last-clicked, for shift-range selection — ordering info a marker can't hold).
Resource
UndoStack — Vec<Box<dyn EditCommand>> plus a cursor. Store edits, not world snapshots: an edit is kilobytes, a snapshot is the whole scene.
Asset
Mesh, Image, StandardMaterial — the actual geometry and materials. Editing geometry means mutating the mesh asset, which every instance sees at once.
State
ToolMode: Select → Move → Rotate → Scale → Sculpt. Each tool's systems are gated by in_state, so tools can't fight over the mouse.
Event
DocumentEdited — sets the dirty flag, invalidates the preview, queues an autosave. Immediate reaction, so an observer rather than a message.
The mistake this genre invites

Keeping selection as Vec<Entity> in a resource. It goes stale the moment something is deleted, it forces every system that cares about selection to iterate the vec and do lookups, and it can't be queried alongside other components. Selection is a property of the thing selected. Keep the resource only for what genuinely isn't per-entity: the anchor, the order, the active tool.

selection, stable ids, and an undo stack
#[derive(Component)]
struct Selected;

// Entity ids are runtime-only. Persist a stable id of your own.
#[derive(Component, Clone, Copy, PartialEq, Eq, Hash)]
#[component(immutable)]
struct ObjectId(Uuid);

// Selection-aware systems are ordinary queries.
fn move_selection(mut q: Query<&mut Transform, With<Selected>>, delta: Res<DragDelta>) {
    for mut t in &mut q { t.translation += delta.0; }
}

fn clear_selection(mut commands: Commands, q: Query<Entity, With<Selected>>) {
    for e in &q { commands.entity(e).remove::<Selected>(); }
}

// Undo: store the inverse edit, never a copy of the world.
trait EditCommand: Send + Sync + 'static {
    fn undo(&self, world: &mut World);
    fn redo(&self, world: &mut World);
}

#[derive(Resource, Default)]
struct UndoStack { done: Vec<Box<dyn EditCommand>>, undone: Vec<Box<dyn EditCommand>> }

// Undo needs &mut World, so run it as an exclusive system.
fn undo(world: &mut World) {
    let Some(cmd) = world.resource_mut::<UndoStack>().done.pop() else { return };
    cmd.undo(world);
    world.resource_mut::<UndoStack>().undone.push(cmd);
}
Editor-specific tooling in 0.19

0.19 shipped a first-party settings framework for exactly this kind of app: derive SettingsGroup on a resource and it loads and saves to disk automatically. It also added a built-in TransformGizmoPlugin and InfiniteGrid, both of which you'd otherwise be building by hand. See Save & load.

RTS / colony sim

Defining problem: thousands of agents that all need to answer "what's near me?" and "what should I do next?" — spatial lookup and task assignment are the data structures that decide whether the game runs.

Component
Unit entity: Transform, UnitKind(Handle<UnitStats>), Health, Faction, and a small Order enum component holding the current command.
Component
Behaviour markers as sparse-set components: Idle, Moving, Attacking, Harvesting. Queries become "all idle workers" instead of a match arm inside a monolithic AI system.
Component
Jobs are entities too, in a colony sim: a Job entity with a location, priority and requirements, linked to its worker by a relationship. Unassigning is removing a component, not mutating two structs in sync.
Resource
SpatialGrid — a uniform grid or quadtree of Entity by cell, rebuilt or incrementally updated each frame. Without it, "enemies within 10m" is O(n²) and dominates your frame.
Resource
FactionRelations (who's hostile to whom), Economy (per-faction stockpiles), Pathfinding grid / navmesh, GameSpeed.
Asset
UnitStats, BuildingDefs, TechTree, RecipeBook — all designer-facing tables. In a colony sim this is most of the game's content, and it should never be Rust constants.
Message
OrderIssued, UnitDied, ResourceDelivered — high volume, many consumers (economy, UI, AI, fog of war), order matters. Classic message territory.
The mistake this genre invites

Nested queries for proximity: for each unit, iterate all units. At 2,000 units that's 4 million distance checks per system per frame. The spatial index is not an optimisation you add later — it changes what your systems look like, so build it in from the first proximity query. Keep it in a resource, rebuild it in a dedicated system before anything reads it, and order everything else after that system.

spatial index + jobs as entities
#[derive(Resource, Default)]
struct SpatialGrid { cell: f32, cells: HashMap<IVec2, Vec<Entity>> }

impl SpatialGrid {
    fn nearby(&self, p: Vec2, r: f32) -> impl Iterator<Item = Entity> + '_ { /* .. */ }
}

// Rebuild once, then everything reads it. Order is the whole trick.
app.add_systems(Update, (
    rebuild_grid,
    (acquire_targets, avoid_crowding, spread_fire).after(rebuild_grid),
));

// ---- Jobs as entities, assigned by relationship ----
#[derive(Component)]
struct Job { site: Vec2, kind: JobKind, priority: u8 }

#[derive(Component)]
#[relationship(relationship_target = AssignedWorkers)]
struct WorkingOn(Entity);

#[derive(Component)]
#[relationship_target(relationship = WorkingOn)]
struct AssignedWorkers(Vec<Entity>);

// "Every idle worker" is now a query, and assigning is one insert.
fn assign(
    idle: Query<Entity, (With<Worker>, Without<WorkingOn>)>,
    jobs: Query<(Entity, &Job), Without<AssignedWorkers>>,
    mut commands: Commands,
) {
    for (worker, (job, _)) in idle.iter().zip(jobs.iter()) {
        commands.entity(worker).insert(WorkingOn(job));
    }
}

2D action roguelike

Defining problem: two lifetimes of data living in one app. Run data dies when you die; profile data must outlive everything. Getting this boundary wrong shows up as either lost unlocks or a "new run" that isn't new.

Resource
RunState — floor number, gold, chosen relics, run seed. Wiped and reinserted on every new run. One resource, one clear reset point.
Resource
PlayerProfile — unlocks, achievements, best times, settings. Never touched by run logic, written to disk on change. Keeping these two in one struct is the bug.
Resource
RunRng — a seeded RNG in its own resource. Never use thread RNG for anything that affects gameplay, or you can't reproduce a run from its seed. Consider one RNG per subsystem (layout, loot, enemies) so adding a loot roll doesn't shift level generation.
Component
Everything in the room: enemies, projectiles, pickups, doors, hazards. Tagged with DespawnOnExit(AppState::InRun) so ending a run cleans the world with no bespoke teardown.
Component
Status effects as sparse-set components: Burning, Slowed, Shielded, each with its own timer field. Adding and removing constantly is exactly what sparse storage is for.
Asset
Room templates, enemy defs, item/relic tables, sprite atlases. Room layouts as data files makes the level designer's loop a file save instead of a compile.
State
AppState: Menu → InRun → GameOver, with a RoomPhase substate for Fighting → Cleared → Choosing reward.
The mistake this genre invites

One giant GameData resource holding run state, profile, settings and cached lookups together. Every system that touches any of it takes ResMut<GameData>, so nothing can run in parallel and resetting a run means carefully clearing half the fields. Split resources by write access — if two systems each need mutable access to different halves, that's two resources.

run vs profile, and a reproducible seed
// Lives for one run. Reset by replacing it wholesale.
#[derive(Resource)]
struct RunState { seed: u64, floor: u32, gold: u32, relics: Vec<RelicId> }

// Lives forever. Only the meta layer writes it.
#[derive(Resource, Default)]
struct PlayerProfile { unlocked: HashSet<RelicId>, best_floor: u32 }

// Separate streams so a new loot roll can't shift level layout.
#[derive(Resource)]
struct LayoutRng(ChaCha8Rng);
#[derive(Resource)]
struct LootRng(ChaCha8Rng);

fn start_run(mut commands: Commands, seed: u64) {
    commands.insert_resource(RunState { seed, floor: 1, gold: 0, relics: vec![] });
    commands.insert_resource(LayoutRng(ChaCha8Rng::seed_from_u64(seed)));
    commands.insert_resource(LootRng(ChaCha8Rng::seed_from_u64(seed ^ 0x9E37_79B9)));
}

// Everything spawned during the run is tagged, so cleanup is automatic.
commands.spawn((Enemy, Transform::from_xyz(x, y, 0.0), DespawnOnExit(AppState::InRun)));

Networked multiplayer

Defining problem: the same entity exists on two machines and its data has to be split into what's replicated, what's predicted, and what's purely local. Getting the split into the type system early saves a rewrite.

Component
Replicated components — the authoritative simulation state, kept deliberately small: position, velocity, health, team. Mark them with a trait or a marker so serialization is derived, not hand-written per type.
Component
Local-only components — particles, audio emitters, interpolation buffers, camera shake, animation state. These must never be replicated, and separating them by component (not by field) is what makes that enforceable.
Component
NetworkId(u64) — a stable id independent of Entity. Two machines will never agree on Entity values, so every cross-machine reference goes through this.
Resource
NetworkMap — HashMap<NetworkId, Entity> both ways, Tick (the simulation tick, not frame count), ServerConfig, InputBuffer of recent local inputs for reconciliation.
Message
Inbound and outbound packets as messages. This is the natural fit: they arrive in batches, several systems care, and the buffering is already built.
Schedule
FixedUpdate holds the simulation; Update holds rendering and interpolation. Replicated data is written only in FixedUpdate, which is what makes rollback tractable.
The mistake this genre invites

Mixing presentation into the components you replicate. Once Player holds both health and muzzle_flash_timer, every state snapshot carries cosmetic data and every rollback stomps your VFX. Draw the line as a component boundary on day one, even if it feels like over-engineering for a two-player prototype.

Change detection, and how to avoid re-doing work

Every component and resource tracks when it was last written. Filter on that instead of recomputing, and you often delete an entire dirty-flag system you wrote by hand.

change detection
// Only entities whose Transform changed since this system last ran.
fn reindex(q: Query<(Entity, &Transform), Changed<Transform>>) { /* .. */ }

// Added<T> = only the frame it appeared.
fn greet(q: Query<&Name, Added<Player>>) { /* .. */ }

// Resources too — skip the whole system if nothing changed.
fn apply_settings(settings: Res<WorldSettings>) {
    if !settings.is_changed() { return; }
}
app.add_systems(Update, apply_settings.run_if(resource_changed::<WorldSettings>));

// Careful: taking ResMut/&mut marks it changed even if you write nothing.
// Guard writes when downstream work is expensive.
if material.base_color != new_color { material.base_color = new_color; }

When you actually need the last 20%

0.19 added contiguous query access, which hands you the raw table slice so LLVM can vectorise. It's the right tool for bulk numeric work over many entities — physics integration, particle updates, mass health decay.

contiguous iteration (0.19)
fn integrate(mut q: Query<(&mut Position, &Velocity)>) {
    for (pos, vel) in q.contiguous_iter_mut().unwrap() {
        for (p, v) in pos.iter_mut().zip(vel) { p.0 += v.0; }
    }
}
// Only works for dense queries: table storage only, and no Changed/Added
// filters (With/Without are fine). Reported ~3x with AVX2 on 10k entities.
// bypass_change_detection() gives raw &mut [T] if you don't need ticks.
Order of operations

Correct storage choices buy you far more than micro-optimisation. In order: pick the right storage kind → don't do O(n²) → batch structural changes → use change detection → then reach for SIMD.

Saving and loading

Three different problems that people often try to solve with one mechanism: user settings, world state, and authored content.

Settings

App settings framework

New in 0.19. Derive SettingsGroup on a resource and Bevy loads it at startup and saves on command — volume, keybinds, graphics, window size, "don't show again".

World state

World serialization

The old bevy_scene, renamed to bevy_world_serialization in 0.19. Round-trips entities and components through reflection. Fine for save games; requires Reflect on everything you keep.

Content

Assets & BSN

Authored content — levels, prefabs, tuning tables — belongs in asset files, loaded not saved. BSN is where this is heading; glTF and RON are where it is today.

settings that persist themselves (0.19)
#[derive(Resource, SettingsGroup, Reflect, Default)]
#[reflect(Resource, SettingsGroup, Default)]
struct AudioSettings { music_volume: f32, sfx_volume: f32 }

// Reverse-domain app id decides where the file lands per platform.
app.add_plugins(SettingsPlugin::new("com.example.mygame"));

// Read it like any other resource; save with SaveSettingsDeferred.
fn apply(audio: Res<AudioSettings>) { /* .. */ }
The rule that saves you

Entity ids are runtime-only. They are indices with generations, they get reused, and they mean nothing across a save/load or across a network. Anything that must survive needs a stable id of your own — ObjectId(Uuid), NetworkId(u64), ChunkCoord(IVec3). Store the stable id in the file and rebuild the Entity mapping on load.

What to serialize

  • Save: authored and simulated state that can't be recomputed — positions, inventories, health, world seed, chunk diffs, quest flags.
  • Don't save: anything derivable — generated meshes, spatial indices, cached lookups, interpolation buffers, visibility, GlobalTransform. Rebuild them on load; it's faster and it can't go stale.
  • For a voxel world specifically: save the seed plus the diff from generated terrain, not the terrain. Orders of magnitude smaller.
07

Traps

Patterns that compile, run, and then cost you a weekend three months later.

Trap

The god resource

One GameState resource holding everything. Every system takes ResMut of it, so the scheduler serialises your whole app and you lose parallelism entirely. Split by writer.

Trap

A component per field

PosX, PosY, PosZ. Every distinct combination is a new archetype, queries get longer, and nothing is faster. Group data that is always read together.

Trap

Hand-rolled Vec<Entity>

Children, inventory contents, squad members. It desynchronises on despawn and leaves dangling ids. Use relationships — they maintain both sides and clean up for you.

Trap

Storing Entity in a save file

Ids are reused after despawn, so a stale one may silently point at a completely different, live entity. Always map through a stable id at the boundary.

Trap

A resource that should be a component

PlayerHealth, CameraPosition, SelectedEntity. Each is a bet that there will only ever be one. Split-screen, minimaps and multi-select all break that bet.

Trap

A component that should be an asset

Full stat blocks copied onto every instance. Duplicated memory, and rebalancing means touching live entities and save files instead of one file.

Trap

Markers churned every frame

Adding and removing a default-storage marker at 60Hz on thousands of entities means an archetype move each time. Either make it sparse set or make it a field.

Trap

Hand-built message queues

A Vec in a resource that you push to and drain next frame. That's Message — with double buffering, independent reader cursors and automatic cleanup already solved.
