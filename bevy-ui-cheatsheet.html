Reference card · verified against Bevy 0.19 (June 2026)

Bevy UIcomplex interfaces

Menus, submenus, inventories, dialogue — the parts that need real data and real state transitions. Bevy UI is flexbox with Rust types and an ECS underneath; once that clicks, the rest is knowing which of the four categories a given API belongs to.

01The mental model

Four sentences that save a lot of confusion later.

  1. A UI element is an entity. Not a widget object — an entity holding a Node component. Nesting is the ECS parent/child relationship (ChildOf), the same one your game objects use.
  2. There are no bundles anymore. Since 0.15, components declare their own dependencies via required components. Spawning Node automatically brings in the machinery it needs. You just spawn tuples of components.
  3. Layout is CSS flexbox. Bevy uses Taffy under the hood. FlexDirection, JustifyContent, AlignItems, and CSS Grid all behave the way they do in a browser. Your CSS instincts transfer almost perfectly.
  4. Reactions come from observers, not polling. Clicking a button triggers an EntityEvent that runs an observer immediately. Buffered Messages are the other tool, for streams you drain each frame.
Why this reference exists

Bevy's UI API has churned hard across 0.15 → 0.19: bundles were removed, Trigger became On, buffered events became Messages, Transform became UiTransform for UI nodes, and 0.19 introduced BSN. Most tutorials you'll find online are written for 0.13–0.16 and will not compile. Everything here is checked against 0.19.

02Cargo & feature flags

0.18 added feature collections, so you can pull in UI without dragging the 3D renderer along.

# Cargo.toml — a normal game
[dependencies]
bevy = "0.19"

# UI-only app (no 3D pipeline, much faster compiles)
bevy = { version = "0.19", default-features = false, features = ["ui"] }

# 2D game + UI
bevy = { version = "0.19", default-features = false, features = ["2d"] }

# Opt into the experimental widget sets
bevy = { version = "0.19", features = [
    "experimental_bevy_ui_widgets",   # headless Button/Slider/Checkbox/Menu
    "experimental_bevy_feathers",     # styled editor-flavoured widgets
    "system_clipboard",               # OS clipboard for text input
] }

The 2d collection is roughly default_app + 2d_api + 2d_bevy_render + ui + scene + audio + picking. Mid-level collections like 2d_api give you the API without Bevy's renderer, if you're swapping in your own.

Minimum viable UI app

use bevy::prelude::*;

fn main() {
    App::new()
        .add_plugins(DefaultPlugins)
        .add_systems(Startup, setup)
        .run();
}

fn setup(mut commands: Commands) {
    // A UI camera is mandatory. Without one you get a blank window.
    commands.spawn(Camera2d);

    commands.spawn((
        Node {
            width: percent(100),
            height: percent(100),
            align_items: AlignItems::Center,
            justify_content: JustifyContent::Center,
            ..default()
        },
        children![(
            Text::new("Hello"),
            TextFont { font_size: 42.0, ..default() },
        )],
    ));
}

Text: the span model layout

A Text node with TextSpan children renders as one continuous paragraph, each span carrying its own font and colour. This is how you build "Press E to open" prompts or coloured damage readouts.

commands.spawn((
    Text::default(),
    children![
        (TextSpan::new("HP "),  TextColor(Color::WHITE)),
        (TextSpan::new("84"),   TextColor(Color::srgb(0.3, 1.0, 0.5))),
        (TextSpan::new("/100"), TextColor(Color::srgb(0.5, 0.5, 0.5))),
    ],
));

// Update just the number later — spans are entities, so query them.
fn update_hp(hp: Res<PlayerHp>, mut q: Query<&mut TextSpan, With<HpNumber>>) {
    if !hp.is_changed() { return; }
    for mut span in &mut q {
        span.0 = hp.current.to_string();
    }
}

Fonts got much better in 0.19

TextFont {
    // Three ways to name a font now:
    font: FontSource::Monospace,                // semantic category
    // font: FontSource::Family("JetBrains Mono".into()),
    // font: FontSource::Handle(asset_server.load("f.ttf")),

    weight: FontWeight::BOLD,                    // variable-font axes
    style:  FontStyle::Italic,
    width:  FontWidth::CONDENSED,

    // font_size is an enum now, not an f32
    font_size: FontSize::Rem(1.5),               // scales with RemSize resource
    ..default()
}

FontSize mirrors CSS: Px, Rem, Vw, Vh, VMin, VMax. Driving everything off Rem gives you one RemSize knob for a UI-scale accessibility slider. Underline, Strikethrough, and LetterSpacing are separate components you add alongside.

04Val & sizing layout

Every length in Bevy UI is a Val. Since 0.17 there are helper functions, and you should use them — they take any integer type and read far better than the enum variants.

Verbose

Node {
    width: Val::Px(200.0),
    padding: UiRect::all(Val::Px(8.0)),
    margin: UiRect::left(Val::Percent(10.0)),
    ..default()
}

Idiomatic 0.19

Node {
    width: px(200),
    padding: px(8).all(),
    margin: percent(10).left(),
    ..default()
}
HelperProducesUse for
px(n)Val::PxFixed sizes, borders, gaps
percent(n)Val::PercentRelative to parent — the workhorse
vw(n) / vh(n)Val::Vw / VhRelative to window; full-screen overlays
vmin(n) / vmax(n)Val::VMin / VMaxAspect-safe sizing across orientations
auto()Val::AutoLet the layout decide

The UiRect builders chain: all, horizontal, vertical, left, right, top, bottom, plus with_* variants to override one side.

// 20% left and right, 10px on top, nothing on the bottom
padding: percent(20).horizontal().with_top(px(10)),
Mixing units

You cannot interpolate between Px and Percent. If you animate a Val (0.18 added TryStableInterpolate for exactly this), keep both keyframes in the same unit or the animation will snap instead of sliding.

justify_content acts along the main axis (the one flex_direction points down); align_items acts across it. Flip to Column above and watch the two controls swap effect — that single behaviour causes most "why won't this centre" confusion.


  
Centring anything, the canonical snippet

Absolute positioning & overlays


Node {
    position_type: PositionType::Absolute,  // out of the flex flow
    left: px(10),
    top: px(10),
    ..default()
}

Node {

    column_gap: px(6),
    ..default()
}

  
Track helpers include px, percent, flex, fr, auto, min_content, max_content. A fixed grid of equal cells is nearly always the right structure for an inventory — you get consistent slot geometry for free.







  
06Spawning trees components

  
Four ways to build a hierarchy. Pick by whether your children are known at compile time.


  
1 — children! for static structure


commands.spawn((
    Node { flex_direction: FlexDirection::Column, ..default() },
    children![
        (Text::new("Title"), TextColor(Color::WHITE)),
        (Button, Node { width: px(120), ..default() }),
    ],
));

  
Nests arbitrarily deep and — since 0.17 — takes as many children as Rust's recursion limit allows (~1400), not the old cap of 12.


  
2 — SpawnIter for data you already have


use bevy::ecs::spawn::SpawnIter;

let entries = [("Display", MenuAction::Display),
               ("Sound",   MenuAction::Sound),
               ("Back",    MenuAction::Back)];

commands.spawn((
    Node { flex_direction: FlexDirection::Column, ..default() },
    Children::spawn(SpawnIter(entries.into_iter().map(|(label, action)| {
        (
            Button,
            Node { width: px(200), height: px(56), ..default() },
            action,
            children![Text::new(label)],
        )
    }))),
));


  
3 — SpawnWith when children need conditional logic


use bevy::ecs::spawn::SpawnWith;

let current = *quality;  // copy out of Res before moving into the closure

Children::spawn(SpawnWith(move |parent: &mut ChildSpawner| {
    for q in [Quality::Low, Quality::Medium, Quality::High] {
        let mut e = parent.spawn((
            Button,
            Node { width: px(150), height: px(65), ..default() },
            q,
            children![Text::new(format!("{q:?}"))],
        ));
        if current == q {
            e.insert(SelectedOption);   // per-child branching
        }
    }
}))

  
SpawnWith is the escape hatch: it hands you a real spawner, so you can branch, count, and insert conditionally. Spawn(...) wraps a single child, and the three compose inside one tuple.


  
4 — helper functions returning impl Bundle


fn menu_button(label: &str, action: MenuAction) -> impl Bundle {
    (
        Button,
        Node {
            width: px(300), height: px(65),
            margin: px(20).all(),
            justify_content: JustifyContent::Center,
            align_items: AlignItems::Center,
            ..default()
        },
        BackgroundColor(NORMAL_BUTTON),
        action,
        children![(Text::new(label), TextFont { font_size: 33.0, ..default() })],
    )
}

// then: children![menu_button("New Game", MenuAction::Play), ...]

  
This is the pattern that scales in 0.19 without BSN. Its one weakness is dependencies: if the bundle needs an asset, you must thread &AssetServer through every call. That's precisely the problem BSN solves.







  
07BSN scenes new in 0.19

  
Bevy Scene Notation is the headline 0.19 feature and it targets UI directly. It's opt-in — the tuple style above still works everywhere — but for deep hierarchies it removes a lot of noise.


  

    Maturity
    
BSN landed in 0.19 and the release notes describe it as "hot off the presses" with rough edges expected for a few releases. The .bsn asset loader is not shipped yet — 0.19 is code-driven only via the bsn! macro. For a shipping project, weigh that against the ergonomics win.

  


  
The basics


// A bsn! block is a list of components for one entity.
// Unspecified fields take their Default — no ..default() needed.
bsn! {
    Node { width: px(300), height: px(65) }
    BackgroundColor(NORMAL_BUTTON)
    Button
}


  
Children inline


fn menu_button(label: &str) -> impl Scene {
    bsn! {
        Button
        Node {
            width: px(300),
            height: px(65),
            justify_content: JustifyContent::Center,
            align_items: AlignItems::Center,
        }
        BackgroundColor(NORMAL_BUTTON)
        Children [
            Text(label)
        ]
    }
}


  
Observers declared in place

  
This is the big one for menus: behaviour and structure live together instead of being wired up in a separate .observe() call.


fn play_button() -> impl Scene {
    bsn! {
        menu_button("New Game")
        on(|_: On<Pointer<Click>>, mut next: ResMut<NextState<GameState>>| {
            next.set(GameState::Game);
        })
    }
}


  
Scenes are patches, so they compose


fn base_button() -> impl Scene {
    bsn! { Button Node { width: px(300) } }
}

fn tall_button() -> impl Scene {
    bsn! {
        base_button()
        Node { height: px(100) }   // layers on top; width survives
    }
}

  
Each layer writes only the fields it names. That's what makes theming and variants tractable — a "danger" variant is just another patch over the base.


  
Lists & passing children as arguments


fn panel(children: impl SceneList) -> impl Scene {
    bsn! {
        Node { flex_direction: FlexDirection::Column, row_gap: px(8) }
        Children [ {children} ]
    }
}

fn main_menu() -> impl Scene {
    panel(bsn_list![
        menu_button("New Game"),
        menu_button("Settings"),
        menu_button("Quit"),
    ])
}


  
Assets by path, no AssetServer plumbing


// Before: every nested bundle fn needed &AssetServer threaded in.
bsn! {
    ImageNode { image: "ui/panel.png" }
}

  
BSN components are templates with access to the World, so a string in an asset field resolves to a Handle at spawn time.


  
SceneComponent: guaranteeing a widget's structure


#[derive(SceneComponent, Default, Clone)]
struct HealthBar { value: f32 }

impl HealthBar {
    fn scene() -> impl Scene {
        bsn! {
            Node { width: px(200), height: px(16) }
            BackgroundColor(Color::BLACK)
            Children [ (#Fill Node { height: percent(100) }) ]
        }
    }
}

// Spawn with @ — the fill child is guaranteed present.
world.spawn_scene(bsn! { @HealthBar { value: 1.0 } });

  
This closes an old Bevy gap: any system querying HealthBar can now assume the fill child exists, because the component cannot be spawned without its scene.


  
Spawning


// From a system
fn setup(mut commands: Commands) {
    commands.spawn_scene(main_menu());
}

// Or turn a scene fn straight into a system
app.add_systems(OnEnter(MenuState::Main), main_menu.spawn());







  
08Events vs Messages events

  
0.17 split one confusing concept into two clear ones. Getting this distinction right is most of "how do I change state from a button".


  

    
EventMessage

    
TraitEvent / EntityEventMessage

    
Sendcommands.trigger(..)MessageWriter::write(..)

    
ReceiveObserver: On<MyEvent>MessageReader<MyMsg>

    
TimingImmediate, at the next command flushBuffered; read when your system runs

    
TargetsCan target an entity and bubble up the treeGlobal stream, no targeting

    
Reach for itUI interactions, one-off reactions, per-entity behaviourHigh-volume streams, input, cross-system fan-out

  


  
Global event


#[derive(Event)]
struct GameOver { score: u32 }

app.add_observer(|game_over: On<GameOver>| {
    info!("scored {}", game_over.score);
});

commands.trigger(GameOver { score: 100 });


  
Entity event — the one UI uses constantly


#[derive(EntityEvent)]
struct SlotClicked {
    entity: Entity,     // field named `entity` becomes the target by default
    slot: usize,
}

commands.trigger(SlotClicked { entity: slot_entity, slot: 4 });

// Global observer: fires for every SlotClicked
app.add_observer(|click: On<SlotClicked>| { /* ... */ });

// Entity observer: only this entity
commands.entity(slot_entity).observe(|click: On<SlotClicked>| { /* ... */ });


  
Use #[event_target] when the target isn't the field called entity:


#[derive(EntityEvent)]
struct Attack {
    #[event_target]
    attacker: Entity,
    victim: Entity,
}


  
Propagation — events bubbling up the UI tree


#[derive(EntityEvent)]
#[entity_event(propagate)]     // walks up ChildOf by default
struct Activate { entity: Entity }

app.add_observer(|mut ev: On<Activate>| {
    if handled {
        ev.propagate(false);              // stop bubbling
    }
    let original = ev.original_event_target();  // deepest node hit
});

  
Propagation is what lets a click on a button's text child be handled by the button. Without it you'd be hit-testing leaf nodes forever.


  
Messages


#[derive(Message)]
struct DamageDealt { amount: f32 }

fn write(mut w: MessageWriter<DamageDealt>) { w.write(DamageDealt { amount: 10.0 }); }
fn read(mut r: MessageReader<DamageDealt>) { for m in r.read() { /* ... */ } }


  

    Renamed in 0.17 — expect stale tutorials
    
Trigger<E> → On<E>. EventWriter/EventReader → MessageWriter/MessageReader. trigger_targets is gone — put the entity on the event and call trigger. Lifecycle events lost their On prefix: OnAdd → Add, so an observer reads On<Add, Player>.

  







  
09Observers in practice events


  
Three ways to attach


// 1. Global — every event of this type
app.add_observer(on_activate);

// 2. Per-entity, at spawn time
commands
    .spawn((Button, Node::default()))
    .observe(|_: On<Pointer<Click>>| info!("clicked"));

// 3. Inside a bsn! scene (0.19)
bsn! { Button on(|_: On<Pointer<Click>>| info!("clicked")) }


  
Observers take full system params


fn on_slot_click(
    click: On<Pointer<Click>>,
    slots: Query<&InventorySlot>,
    mut inventory: ResMut<Inventory>,
    mut commands: Commands,
) {
    let Ok(slot) = slots.get(click.entity) else { return };
    inventory.select(slot.index);
}


  
Run conditions on observers 0.19


app.add_observer(
    on_slot_click
        .run_if(in_state(GameState::Playing))
        .run_if(|p: Res<Paused>| !p.0)
);

  
New in 0.19 and genuinely useful: previously you had to early-return inside the observer body to gate on state.


  
Lifecycle observers — react to UI being built


// Fires whenever a Tooltip component is added to any entity
app.add_observer(|add: On<Add, Tooltip>, mut commands: Commands| {
    commands.entity(add.entity).insert(GlobalZIndex(100));
});

  
Available lifecycle events: Add, Insert, Replace, Remove, Despawn.


  

    Observers vs polling systems
    
Observers run at command-flush time, not in your schedule order. Don't rely on an observer having run before a specific system in the same frame. When ordering genuinely matters, have the observer write a Message or set a component, and let an ordered system act on it.

  







  
10Pointer events events

  
All wrapped in Pointer<T>, delivered to the entity under the cursor, and bubbling up the hierarchy.


  

  

    
EventFires

    
Pointer<Over>Cursor enters the node's bounds

    
Pointer<Out>Cursor leaves

    
Pointer<Move>Cursor moves while over the node

    
Pointer<Press>Button pressed down on the node

    
Pointer<Release>Button released

    
Pointer<Click>Press and release on the same node — carries duration, so you can detect long-press

    
Pointer<DragStart>Press then move begins a drag

    
Pointer<Drag>Each frame during a drag; carries delta and distance

    
Pointer<DragEnd>Drag finishes

    
Pointer<DragEnter>A dragged thing enters this node

    
Pointer<DragOver>A dragged thing hovers this node

    
Pointer<DragDrop>A dragged thing is dropped on this node — the inventory workhorse

    
Pointer<DragLeave>A dragged thing leaves this node

    
Pointer<Cancel>Interaction aborted; nothing else follows

  

  


  
Within a frame the dispatch order is fixed: Out → DragLeave, then DragEnter → Over, then per movement DragStart → Drag → DragOver → Move, then per press Press or Click → Release → DragDrop → DragEnd → DragLeave.


  
Hover styling without a polling system


commands
    .spawn((Button, Node::default(), BackgroundColor(NORMAL)))
    .observe(|over: On<Pointer<Over>>, mut q: Query<&mut BackgroundColor>| {
        if let Ok(mut bg) = q.get_mut(over.entity) { bg.0 = HOVERED; }
    })
    .observe(|out: On<Pointer<Out>>, mut q: Query<&mut BackgroundColor>| {
        if let Ok(mut bg) = q.get_mut(out.entity) { bg.0 = NORMAL; }
    });


  
The older Interaction path

  
The legacy polling API still ships and still works — Bevy's own game_menu example uses it in 0.19. It's fine for simple menus and easier to reason about ordering with.


fn button_colors(
    mut q: Query<(&Interaction, &mut BackgroundColor),
                 (Changed<Interaction>, With<Button>)>,
) {
    for (interaction, mut bg) in &mut q {
        *bg = match *interaction {
            Interaction::Pressed  => PRESSED.into(),
            Interaction::Hovered  => HOVERED.into(),
            Interaction::None     => NORMAL.into(),
        };
    }
}

  
The Changed<Interaction> filter matters — without it you rewrite every button's colour every frame.







  
11States state

  
States are how screens get created and destroyed. Menus are almost entirely a state-machine problem with some flexbox attached.



#[derive(States, Clone, Copy, Default, Eq, PartialEq, Debug, Hash)]
enum GameState {
    #[default]
    Splash,
    Menu,
    Game,
}

app.init_state::<GameState>()
   .add_systems(OnEnter(GameState::Menu), spawn_menu)
   .add_systems(OnExit(GameState::Menu),  cleanup_menu)
   .add_systems(Update, tick.run_if(in_state(GameState::Game)));

// Transition from anywhere:
fn start(mut next: ResMut<NextState<GameState>>) {
    next.set(GameState::Game);
}


  
DespawnOnExit — delete the cleanup boilerplate


commands.spawn((
    DespawnOnExit(MenuState::Main),   // whole subtree dies on state exit
    Node { width: percent(100), height: percent(100), ..default() },
    children![ /* ... */ ],
));

  
You no longer need a marker component plus a despawn_all::<T> generic system on every screen. Put it on the root node and the children go with it.


  
Sub-states — pause menus that only exist in-game


#[derive(SubStates, Clone, Copy, Default, Eq, PartialEq, Debug, Hash)]
#[source(GameState = GameState::Game)]
enum PauseState {
    #[default]
    Running,
    Paused,
}

app.add_sub_state::<PauseState>();

  
PauseState only exists while GameState::Game is active, and is removed automatically on exit — so a paused game can't leak a pause overlay into the main menu. ComputedStates is the sibling API for states derived from others (e.g. "is any menu open").







  
12Menus, end to end

  
The architecture Bevy's own game_menu example uses, condensed. Two states: one for the app, one for which menu screen is showing.



#[derive(States, Clone, Copy, Default, Eq, PartialEq, Debug, Hash)]
enum MenuState {
    Main,
    Settings,
    SettingsDisplay,
    SettingsSound,
    #[default]
    Disabled,          // nothing showing — the menu isn't open
}

#[derive(Component)]
enum MenuButtonAction {
    Play, Settings, SettingsDisplay, SettingsSound,
    BackToMainMenu, BackToSettings, Quit,
}

pub fn menu_plugin(app: &mut App) {
    app.init_state::<MenuState>()
        // entering GameState::Menu switches the inner state on
        .add_systems(OnEnter(GameState::Menu), |mut m: ResMut<NextState<MenuState>>| {
            m.set(MenuState::Main);
        })
        // one setup system per screen
        .add_systems(OnEnter(MenuState::Main), main_menu_setup)
        .add_systems(OnEnter(MenuState::Settings), settings_setup)
        .add_systems(OnEnter(MenuState::SettingsDisplay), display_setup)
        .add_systems(OnEnter(MenuState::SettingsSound), sound_setup)
        // one action handler for all of them
        .add_systems(Update, menu_action.run_if(in_state(GameState::Menu)));
}


  
The single action handler


fn menu_action(
    q: Query<(&Interaction, &MenuButtonAction), (Changed<Interaction>, With<Button>)>,
    mut exit: MessageWriter<AppExit>,
    mut menu: ResMut<NextState<MenuState>>,
    mut game: ResMut<NextState<GameState>>,
) {
    for (interaction, action) in &q {
        if *interaction != Interaction::Pressed { continue; }
        match action {
            MenuButtonAction::Quit => { exit.write(AppExit::Success); }
            MenuButtonAction::Play => {
                game.set(GameState::Game);
                menu.set(MenuState::Disabled);   // tear the menu down
            }
            MenuButtonAction::Settings        => menu.set(MenuState::Settings),
            MenuButtonAction::SettingsDisplay => menu.set(MenuState::SettingsDisplay),
            MenuButtonAction::SettingsSound   => menu.set(MenuState::SettingsSound),
            MenuButtonAction::BackToMainMenu  => menu.set(MenuState::Main),
            MenuButtonAction::BackToSettings  => menu.set(MenuState::Settings),
        }
    }
}


  

    Why this scales
    
Buttons carry an action component rather than a callback. Adding a screen means adding an enum variant, an OnEnter system, and a match arm — never touching the others. And because each screen root carries DespawnOnExit, transitions clean up for free.

  


  
Settings buttons with a generic system

  
A neat trick from the official example: make the setting value itself a component, then write one generic system for every setting type.


#[derive(Resource, Component, Debug, PartialEq, Eq, Clone, Copy)]
enum DisplayQuality { Low, Medium, High }

#[derive(Component)]
struct SelectedOption;

fn setting_button<T: Resource + Component + PartialEq + Copy>(
    q: Query<(&Interaction, &T, Entity), (Changed<Interaction>, With<Button>)>,
    selected: Single<(Entity, &mut BackgroundColor), With<SelectedOption>>,
    mut commands: Commands,
    mut setting: ResMut<T>,
) {
    let (prev, mut prev_color) = selected.into_inner();
    for (interaction, value, entity) in &q {
        if *interaction == Interaction::Pressed && *setting != *value {
            *prev_color = NORMAL.into();
            commands.entity(prev).remove::<SelectedOption>();
            commands.entity(entity).insert(SelectedOption);
            *setting = *value;
        }
    }
}

// Register once per setting type:
app.add_systems(Update, (
    setting_button::<DisplayQuality>.run_if(in_state(MenuState::SettingsDisplay)),
    setting_button::<Volume>.run_if(in_state(MenuState::SettingsSound)),
));







  
13Submenu stacks & back navigation

  
Flat states break down once "Back" has to remember where you came from. Two solutions, depending on depth.


  
Shallow: hardcode the return target

  
With three or four screens, BackToSettings and BackToMainMenu as separate actions is honest and readable. Don't over-engineer.


  
Deep: keep an explicit stack


#[derive(Resource, Default)]
struct MenuStack(Vec<MenuState>);

#[derive(Event)]
struct PushMenu(MenuState);

#[derive(Event)]
struct PopMenu;

fn on_push(
    push: On<PushMenu>,
    current: Res<State<MenuState>>,
    mut stack: ResMut<MenuStack>,
    mut next: ResMut<NextState<MenuState>>,
) {
    stack.0.push(*current.get());
    next.set(push.0);
}

fn on_pop(
    _: On<PopMenu>,
    mut stack: ResMut<MenuStack>,
    mut next: ResMut<NextState<MenuState>>,
) {
    if let Some(prev) = stack.0.pop() {
        next.set(prev);
    } else {
        next.set(MenuState::Main);
    }
}

// Escape key pops, universally:
fn escape_pops(keys: Res<ButtonInput<KeyCode>>, mut commands: Commands) {
    if keys.just_pressed(KeyCode::Escape) {
        commands.trigger(PopMenu);
    }
}


  
Overlay submenus that don't destroy the parent

  
Sometimes a submenu should sit on top of the menu behind it rather than replacing it — a confirmation dialog, say. Don't model that as a state transition; spawn a modal and dim the parent.


commands.spawn((
    ConfirmDialog,
    GlobalZIndex(100),                      // above everything
    Node {
        position_type: PositionType::Absolute,
        width: percent(100), height: percent(100),
        align_items: AlignItems::Center,
        justify_content: JustifyContent::Center,
        ..default()
    },
    BackgroundColor(Color::srgba(0., 0., 0., 0.7)),  // scrim blocks clicks
    children![ /* the dialog box */ ],
));

  
The full-screen scrim is doing real work: because it's a node with default Pickable behaviour, it absorbs pointer events and the menu behind becomes unclickable without any extra input gating.

}

17Binding data to UI state

  
"Stuff that needs data" is where most Bevy UI code goes wrong. There is no reactive binding layer — you choose an update strategy, and the wrong one is either a stutter or a bug.


  
Strategy 1 — change detection (default choice)


fn sync_gold_label(
    wallet: Res<Wallet>,
    mut q: Query<&mut Text, With<GoldLabel>>,
) {
    if !wallet.is_changed() { return; }        // cheap early out
    for mut text in &mut q {
        **text = format!("{} gold", wallet.gold);
    }
}

// Or gate the whole system:
app.add_systems(Update, sync_gold_label.run_if(resource_changed::<Wallet>));

  
Mutate the UI in place; never despawn and respawn a label to change its text.


  
Strategy 2 — observers on data changes


// Push-based: the data layer announces, the UI listens.
#[derive(Event)]
struct InventoryChanged;

app.add_observer(|_: On<InventoryChanged>,
                  inv: Res<Inventory>,
                  mut commands: Commands,
                  slots: Query<Entity, With<SlotIcon>>| {
    // rebuild only the icons, not the whole panel
});

  
Better than change detection when the update is expensive and rare: you rebuild exactly when something happened rather than checking every frame.


  
Strategy 3 — marker components carrying an index


#[derive(Component)]
struct SlotIndex(usize);

fn sync_slots(
    inv: Res<Inventory>,
    mut q: Query<(&SlotIndex, &mut ImageNode)>,
    assets: Res<AssetServer>,
) {
    if !inv.is_changed() { return; }
    for (idx, mut image) in &mut q {
        image.image = match inv.slots.get(idx.0) {
            Some(Some(item)) => assets.load(item.icon_path()),
            _ => assets.load("ui/empty_slot.png"),
        };
    }
}

  
Spawn a fixed number of slot entities once, then only ever mutate their contents. This is the single most important performance pattern for inventories.


  

    The mistake to avoid
    
Despawning and respawning a UI subtree every frame — or every time data changes — thrashes the layout engine, destroys focus, kills any in-progress drag, and resets scroll position. Build once, mutate in place, and only rebuild when the structure genuinely changes (item count, not item value).

  







  
18Inventories

  
A grid of slot entities, a data source, and drag-and-drop. The interesting decision is how items relate to the player.


  
Option A — relationships (ECS-native)


#[derive(Component)]
#[relationship(relationship_target = Inventory)]
struct StoredIn(Entity);

#[derive(Component)]
#[relationship_target(relationship = StoredIn)]
struct Inventory(Vec<Entity>);

// Items are real entities with real components.
commands.spawn((Item, Name::new("Iron Sword"), Damage(12), StoredIn(player)));

// Query the contents:
fn list(inv: Query<&Inventory>, items: Query<&Name>) {
    for inventory in &inv {
        for &item in inventory.iter() {
            if let Ok(name) = items.get(item) { info!("{name}"); }
        }
    }
}

  
Items get the full ECS: components for stats, observers for behaviour, queries across all items in the world. Bevy maintains both sides of the relationship automatically. In BSN you can spawn related entities inline with Inventory [ Apple, Potion ].


  
Option B — a plain resource


#[derive(Resource, Default)]
struct PlayerInventory {
    slots: Vec<Option<ItemStack>>,
}

#[derive(Clone)]
struct ItemStack { id: ItemId, count: u32 }

  
Simpler to serialise, simpler to reason about, trivially cloneable for undo. Choose this if items are mostly data rather than behaviour. Don't feel obliged to make everything an entity.

Drag and drop


#[derive(Resource, Default)]
struct DragSource(Option<usize>);

fn setup_slot_observers(mut commands: Commands, slots: Query<Entity, With<SlotIndex>>) {
    for slot in &slots {
        commands.entity(slot)
            .observe(|start: On<Pointer<DragStart>>,
                      q: Query<&SlotIndex>,
                      mut drag: ResMut<DragSource>| {
                if let Ok(idx) = q.get(start.entity) { drag.0 = Some(idx.0); }
            })
            .observe(|drop: On<Pointer<DragDrop>>,
                      q: Query<&SlotIndex>,
                      mut drag: ResMut<DragSource>,
                      mut inv: ResMut<PlayerInventory>| {
                let (Some(from), Ok(to)) = (drag.0.take(), q.get(drop.entity)) else { return };
                inv.slots.swap(from, to.0);   // change detection fires; UI resyncs
            });
    }
}


  
Drag ghost

  
For an icon that follows the cursor, spawn one absolutely-positioned node with a high GlobalZIndex on DragStart, move it on Pointer<Drag> using drag.delta, and despawn it on DragEnd. Give it Pickable::IGNORE — otherwise the ghost sits under the cursor and eats the DragDrop event meant for the slot beneath it.


  
Tooltips

  
Popover anchored to the hovered slot handles placement and edge-flipping for you. Show it on Pointer<Over>, hide on Pointer<Out>, and add a short delay via a timer so tooltips don't strobe as the cursor crosses the grid.







  
19Dialogue

  
Conversation is a small state machine plus text reveal. Keep the dialogue data out of the UI code entirely.


  
Data model


#[derive(Asset, Reflect, Clone)]
struct DialogueTree {
    nodes: HashMap<NodeId, DialogueNode>,
    start: NodeId,
}

#[derive(Reflect, Clone)]
struct DialogueNode {
    speaker: String,
    line: String,
    choices: Vec<Choice>,     // empty = press to continue
}

#[derive(Reflect, Clone)]
struct Choice {
    text: String,
    goto: Option<NodeId>,       // None = end conversation
}

#[derive(Resource)]
struct ActiveDialogue {
    tree: Handle<DialogueTree>,
    current: NodeId,
    revealed: usize,        // chars shown so far
    timer: Timer,
}


  
Advancing, as events


#[derive(Event)]
struct AdvanceDialogue;

#[derive(Event)]
struct ChooseOption(usize);

#[derive(Event)]
struct DialogueEnded(NodeId);   // quest systems observe this

fn on_advance(
    _: On<AdvanceDialogue>,
    mut active: ResMut<ActiveDialogue>,
    trees: Res<Assets<DialogueTree>>,
    mut commands: Commands,
) {
    let Some(tree) = trees.get(&active.tree) else { return };
    let node = &tree.nodes[&active.current];

    // First press completes the typewriter instead of advancing —
    // players expect this and its absence feels broken.
    if active.revealed < node.line.chars().count() {
        active.revealed = node.line.chars().count();
        return;
    }

    match node.choices.first() {
        None => { commands.trigger(DialogueEnded(active.current)); }
        Some(_) => { /* wait for ChooseOption */ }
    }
}


  
Typewriter reveal


fn typewriter(
    time: Res<Time>,
    mut active: ResMut<ActiveDialogue>,
    trees: Res<Assets<DialogueTree>>,
    mut q: Query<&mut Text, With<DialogueLine>>,
) {
    let Some(tree) = trees.get(&active.tree) else { return };
    let full = &tree.nodes[&active.current].line;
    let total = full.chars().count();
    if active.revealed >= total { return; }

    active.timer.tick(time.delta());
    if active.timer.just_finished() {
        active.revealed = (active.revealed + 1).min(total);
        for mut text in &mut q {
            **text = full.chars().take(active.revealed).collect();
        }
    }
}

  
Count chars(), not bytes — slicing a String by byte index will panic the moment someone writes an accented character or an emoji.


  
Choice buttons

  
Choices are structural change, so respawning them per node is correct here — unlike inventory slots. Spawn them with SpawnIter over the node's choices, each carrying a ChoiceIndex component, and have their observer trigger ChooseOption(index).


  

    Keep the seam clean
    
The dialogue UI should read ActiveDialogue and emit events. It should never mutate quest flags or inventory directly. Then your dialogue system is testable headlessly, and swapping in a different UI skin touches nothing else.

22Gotchas & performance


  
    
    
  • No UI camera, no UI. Spawn a Camera2d (or use an existing 3D camera). The most common "nothing renders" cause.
    • 
    
  • Filter interaction queries. Changed<Interaction> turns a per-frame loop over every button into an occasional one.
    • 
    
  • Don't rebuild subtrees for value changes. Mutate components in place. Rebuild only when structure changes.
    • 
    
  • Use GlobalZIndex for modals. Local ZIndex only orders siblings; a deeply nested dialog can't escape its parent's stacking context without it.
    • 
    
  • Pickable::IGNORE on decorative overlays. Vignettes, drag ghosts, and full-screen effects silently swallow clicks otherwise.
    • 
    
  • Text is a child entity. A button's text is its own entity, so a naive click handler may target the text. Rely on event propagation, or query up with ChildOf.
    • 
    
  • Percentage heights need a sized parent. Same trap as CSS: height: percent(100) inside an auto-height parent resolves to nothing.
    • 
    
  • Observers aren't schedule-ordered. Don't assume an observer ran before a given system this frame.
    • 
    
  • Watch UiTransform, not Transform. Since 0.17, UI nodes use UiTransform; writing Transform on a UI node does nothing.
    • 
    
  • Prefer a fixed pool of slot entities over spawn/despawn churn for grids and lists.
    •
