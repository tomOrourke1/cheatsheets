WGSL · wgpu · Rust — fragment-shader reference

You have one triangle
and a loop.

Rasterization asks where does this triangle land? Raymarching asks the opposite: for every pixel, shoot a ray into the scene and walk along it until something stops you. Everything else — geometry, normals, shadows, fog — falls out of how you take that walk.

This is the reference for the walk itself: how the ray gets built, what governs the step size, what breaks when the step size lies to you, and how to do all of it inside WGSL's particular constraints.

Sphere tracing. Each circle is the distance to the nearest surface — provably empty, so the ray can jump the whole radius. step 0

Step 1 — the surface you draw on

Get a fragment shader running over every pixel, with nothing in the way

You need one draw call that covers the screen and carries no geometry information at all. The usual answer is a fullscreen triangle — not a quad. One oversized triangle clipped to the viewport avoids the diagonal seam where two quad triangles meet, where quads waste a row of helper invocations.

wgslno vertex buffer, no index buffer, three vertices
@vertex
fn vs_main(@builtin(vertex_index) vi: u32) -> @builtin(position) vec4f {
    // vi = 0,1,2  ->  uv = (0,0), (2,0), (0,2)
    let uv = vec2f(f32((vi << 1u) & 2u), f32(vi & 2u));
    // ...which maps to clip positions (-1,-1), (3,-1), (-1,3)
    return vec4f(uv * 2.0 - 1.0, 0.0, 1.0);
}

The uniform block, and the alignment rule that will bite you

A vec3f occupies 12 bytes but aligns to 16. If your Rust struct packs three floats followed by two more, WGSL will read from different offsets than Rust wrote to, and you will get a scene that jitters, tilts, or vanishes. Pad explicitly and keep the total a multiple of 16.

rustbyte offsets annotated — match these exactly
#[repr(C)]
#[derive(Copy, Clone, bytemuck::Pod, bytemuck::Zeroable)]
struct Uniforms {
    resolution: [f32; 2],   //  0..8    vec2f, align 8
    time:       f32,        //  8..12
    fov_y:      f32,        // 12..16   (radians)
    eye:        [f32; 3],   // 16..28   vec3f, align 16 -> must start at 16
    _pad0:      f32,        // 28..32
    target:     [f32; 3],   // 32..44
    _pad1:      f32,        // 44..48   total 48 = 3 * 16  ✓
}

Trap

Turning on MSAA does nothing for a raymarched image. Multisampling antialiases primitive edges, and your entire frame is the interior of one triangle. Every visible edge is a discontinuity in the fragment shader's own output, which MSAA never sees. Your options are supersampling (render bigger, downsample), temporally jittering the ray direction and accumulating, or computing coverage analytically inside the shader.

Everything from here lives in fs_main. Rebuild the uniform buffer per frame with queue.write_buffer; you should never need to touch the pipeline again, including on resize.

Step 2 — from pixel to ray

Every raymarcher starts by inventing a camera out of a pixel coordinate

There are exactly three things to get right: the coordinate normalization, the handedness of the camera basis, and the focal length. Getting any of them subtly wrong produces an image that looks plausible and matches nothing.

Normalizing the pixel coordinate

@builtin(position) in a fragment shader is in framebuffer pixels, origin at the top-left, y increasing downward, sampled at pixel centers (so the first pixel is 0.5, not 0.0). Convert to a centered, y-up, aspect-correct coordinate:

screen coordinateuv = (2·pos.xy − res) / res.y , then uv.y ← −uv.y

Dividing both components by res.y is deliberate. It makes uv.y ∈ [−1, 1] and lets uv.x run wider on wide screens — so the vertical field of view is fixed and horizontal FOV grows with the window, which is what almost every game does. Dividing by res componentwise instead stretches the image when the aspect changes.

Focal length

With uv.y ∈ [−1,1], placing the image plane at distance f along forward gives a half-angle of atan(1/f). So:

focal length from vertical fovf = 1 / tan(fov_y / 2) // identical to proj[1][1] in a perspective matrix

That equality is the useful part: use it and your raymarched scene lines up with anything you rasterize through the same projection.

wgslray generation, look-at camera
fn camera_basis(eye: vec3f, target: vec3f, roll: f32) -> mat3x3f {
    let fwd   = normalize(target - eye);
    let wup   = vec3f(sin(roll), cos(roll), 0.0);     // roll = tilt the horizon
    let right = normalize(cross(fwd, wup));
    let up    = cross(right, fwd);                    // already unit + orthogonal
    return mat3x3f(right, up, fwd);                   // columns, in that order
}

@fragment
fn fs_main(@builtin(position) pos: vec4f) -> @location(0) vec4f {
    var uv = (2.0 * pos.xy - u.resolution) / u.resolution.y;
    uv.y = -uv.y;                                     // framebuffer y is down

    let cam   = camera_basis(u.eye, u.target, 0.0);
    let focal = 1.0 / tan(0.5 * u.fov_y);

    let ro = u.eye;
    let rd = normalize(cam * vec3f(uv, focal));       // column-major: r*x + u*y + f*z
    // ...
}
Trap

When fwd becomes parallel to the world up vector — looking straight down — cross(fwd, wup) is the zero vector, normalize returns NaN, and the NaN spreads through every subsequent min and max until the pixel is black or white garbage. Either clamp the pitch short of ±90°, or feed the basis in directly as a mat3x3f uniform built on the CPU where you can handle the degenerate case in Rust.

Alternative: unproject through the inverse view-projection

If a camera controller already owns a view_proj matrix, skip the basis construction entirely and reuse it. This is the approach to prefer when the raymarched pass has to agree with rasterized geometry down to the pixel.

wgslmatrix-driven ray, WebGPU NDC
// WebGPU clip space: x,y in [-1,1] (y UP), z in [0,1]  (0 = near, 1 = far)
var ndc = vec2f(2.0 * pos.xy / u.resolution - 1.0);
ndc.y = -ndc.y;

let far  = u.inv_view_proj * vec4f(ndc, 1.0, 1.0);
let ro   = u.eye;
let rd   = normalize(far.xyz / far.w - ro);
Remember

WebGPU depth is 0 to 1, not −1 to 1 as in OpenGL. Ported GLSL that unprojects with z = -1.0 for the near plane will produce a ray pointing somewhere behind the camera. glam's Mat4::perspective_rh already targets 0..1, so it pairs correctly.

Step 3 — the march

Four ways to walk a ray, and what each one demands of your field

The march is a loop that advances a scalar t along p = ro + rd·t and asks a question at each position. What changes between techniques is what the question returns and therefore how far you're allowed to move next. That single choice determines the cost, the artifacts, and what kinds of geometry you can represent.

The sphere-tracing loop, written for real use

Return more than a boolean. t gives you the hit position and fog; the step count is your only performance debugging tool; a material id lets one march shade a whole scene.

wgslmap() returns vec2f(distance, material_id)
const MAX_STEPS: i32 = 128;
const MAX_DIST:  f32 = 100.0;
const EPS:       f32 = 0.0008;

struct Hit {
    t:     f32,
    id:    f32,     // -1.0 = miss
    steps: f32,     // keep it; you will need it
};

fn march(ro: vec3f, rd: vec3f) -> Hit {
    var t = 0.0;
    var i = 0;
    loop {
        if (i >= MAX_STEPS) { break; }
        let p = ro + rd * t;
        let h = map(p);

        // epsilon grows with distance: one pixel covers more world space far away
        if (h.x < EPS * max(t, 1.0)) {
            return Hit(t, h.y, f32(i));
        }
        t += h.x;
        if (t > MAX_DIST) { break; }
        i += 1;
    }
    return Hit(t, -1.0, f32(i));
}
Why this is fast, and why it isn't

Sphere tracing is fast because in open space each step is enormous — the ray crosses empty regions in two or three iterations. It is slow because a ray traveling nearly parallel to a surface stays a hair's breadth away for a long distance and takes microscopic steps the whole way. Those grazing rays are what burn your frame budget, and because a GPU runs pixels in lockstep groups, one crawling pixel stalls everything scheduled alongside it. Cap MAX_STEPS and accept the artifact; the alternative is a 4 ms frame becoming 40 ms.

Fixed-step accumulation

Nothing here is a surface. You sample a scalar field at even intervals and integrate what you find. No distance property is required, so any function of position works — noise, a 3D texture, an analytic falloff.

wgslfront-to-back, Beer–Lambert
fn march_volume(ro: vec3f, rd: vec3f, t_near: f32, t_far: f32, seed: f32) -> vec4f {
    let steps = 64;
    let dt = (t_far - t_near) / f32(steps);

    var t = t_near + fract(seed) * dt;      // jitter kills the banding
    var accum = vec3f(0.0);
    var transmittance = 1.0;

    for (var i = 0; i < steps; i++) {
        let p = ro + rd * t;
        let density = max(0.0, fbm(p));

        if (density > 0.001) {
            // absorption over one slab of thickness dt
            let a = 1.0 - exp(-density * dt * SIGMA);
            let lit = light_march(p);       // a second, shorter march toward the sun
            accum += transmittance * a * lit;
            transmittance *= 1.0 - a;
            if (transmittance < 0.01) { break; }
        }
        t += dt;
    }
    return vec4f(accum, 1.0 - transmittance);
}

The exponential is not decoration. Transmittance through a medium is exp(−σ · ∫ρ ds); using 1 − density·dt instead is a linear approximation that goes visibly wrong as soon as dt changes, so dropping your step count will also change the brightness of the result.

Step and refine

When your function is signed but carries no distance meaning — a heightfield difference, a polynomial, a noise isosurface — you cannot trust its magnitude, only its sign. March in small steps, watch for the sign to flip, then find the crossing between the last two samples.

wgslterrain: march, detect crossing, interpolate
fn march_terrain(ro: vec3f, rd: vec3f) -> f32 {
    var t = 0.1;
    var last_t = t;
    var last_h = ro.y - height(ro.xz);       // > 0 above the ground

    for (var i = 0; i < 200; i++) {
        let p = ro + rd * t;
        let h = p.y - height(p.xz);

        if (h < 0.0) {
            // linear crossing between last_t and t — usually enough
            return mix(last_t, t, last_h / (last_h - h));
        }
        last_t = t;
        last_h = h;

        t += max(0.02, 0.35 * h);            // heuristic: big steps when high up
        if (t > 400.0) { break; }
    }
    return -1.0;
}

The step heuristic 0.35 * h is a guess, not a bound — it works because terrain slopes are limited. Steepen the terrain and it starts tunneling through ridges. If you need it robust, swap the linear interpolation for four or five bisection iterations and shrink the step multiplier.

Step 4 — the math you cannot fudge

Sphere tracing is only correct while your function is 1-Lipschitz

This is the single idea that explains most raymarching bugs. Stepping by d = map(p) is safe only if moving a distance d cannot possibly reach a surface. Formally, map must not change faster than position does:

the Lipschitz condition| map(a) − map(b) | ≤ K · | a − b | with K ≤ 1

When K ≤ 1, the sphere of radius d around p is guaranteed empty and you can jump the whole way. When K > 1 — when your field changes faster than distance — you step past surfaces. The visible result is holes in thin geometry, dark banding on shallow slopes, and edges that look eroded. The fix is always the same: divide by K, or multiply your step by 1/K.

The one-line diagnostic

If your scene has mysterious dark bands or dissolving edges, change t += h.x to t += h.x * 0.5. If the artifacts disappear, you have a Lipschitz problem, not a bug — go find which operation is inflating your gradient. If they persist, look at your epsilon instead.

Epsilon: the other half of the problem

A fixed epsilon is wrong at both ends of the depth range. Too large and near-camera surfaces look inflated and rounded; too small and distant surfaces shimmer as rays fail to converge before the step cap. The principled value is the width of a pixel at that distance — a ray isn't a line, it's a cone.

pixel footprint at distance tε(t) = t · tan(fov_y / 2) · 2 / res.y
wgslcone-aware epsilon, computed once per pixel
// pass this into march() — one multiply per step, no per-step divide
let px = 2.0 * tan(0.5 * u.fov_y) / u.resolution.y;   // radians per pixel
// inside the loop:
if (h.x < max(0.5 * px * t, MIN_EPS)) { /* hit */ }

Over-relaxation, when you actually need the speed

Sphere tracing is conservative by construction — it usually could have gone further. Enhanced sphere tracing steps by ω · d with ω ∈ [1, 2) and backtracks whenever the new bounding sphere fails to contain the previous one. It typically saves 20–40% of steps on scenes with lots of open space, and costs you a branch.

wgslKeinert et al., enhanced sphere tracing
var t = 0.0;
var prev_radius = 0.0;
var step_len = 0.0;
let omega = 1.6;

for (var i = 0; i < MAX_STEPS; i++) {
    let radius = map(ro + rd * t).x;
    let overstepped = step_len > radius + prev_radius;   // spheres don't overlap

    if (overstepped) {
        step_len -= omega * step_len;                    // back off, retry safely
        t += step_len;
        prev_radius = 0.0;
    } else {
        if (radius < EPS * t) { break; }
        step_len = radius * omega;
        t += step_len;
        prev_radius = radius;
    }
}

Float precision

WGSL gives you f32 and nothing else unless you enable the shader-f16 feature. At t = 1000, the gap between representable floats is around 6e-5, so an epsilon of 1e-5 is arithmetically unreachable and the loop spins until the step cap. Two practical consequences: keep your scene near the origin, and if you want infinite worlds, fold the domain (p - s * round(p / s)) rather than translating the camera into large coordinates.

Step 5 — what you know at the hit

You have a point and a scalar field. Everything else is a derivative

Rasterization hands you interpolated normals, UVs and tangents for free. Raymarching hands you a position, and you reconstruct the rest by sampling the field again around it. Each sample is a full evaluation of map, so this is where a cheap-looking shader becomes expensive.

Normals by finite differences

The gradient of a distance field points away from the surface, and on the surface it has unit length — so normalize(∇map) is the normal. The naive central difference costs six evaluations. The tetrahedron trick costs four, by sampling the four corners of a tetrahedron instead of the six faces of a cube:

wgsl4-tap tetrahedron gradient
fn calc_normal(p: vec3f, h: f32) -> vec3f {
    let k = vec2f(1.0, -1.0) * 0.5773502692 * h;   // 1/sqrt(3)
    return normalize(
        k.xyy * map(p + k.xyy).x +
        k.yyx * map(p + k.yyx).x +
        k.yxy * map(p + k.yxy).x +
        k.xxx * map(p + k.xxx).x
    );
}
Scale h with distance

A fixed h of 0.0001 is fine at two units away and produces pure noise at two hundred, because the difference between the four samples drops below float precision. Use the same pixel-footprint value you used for epsilon: calc_normal(p, max(0.5 * px * t, 1e-4)). Normals that sparkle in the distance are almost always this and not a lighting bug.

Materials without branching per primitive

Have map return a vec2f: distance in .x, an id in .y. Combine with a min that carries the id along:

wgslid-carrying union
fn op_union(a: vec2f, b: vec2f) -> vec2f {
    return select(b, a, a.x < b.x);      // note: select(false_val, true_val, cond)
}

fn map(p: vec3f) -> vec2f {
    var d = vec2f(p.y + 1.0, 1.0);                    // ground, id 1
    d = op_union(d, vec2f(sd_sphere(p - vec3f(0.0, 0.0, 0.0), 1.0), 2.0));
    d = op_union(d, vec2f(sd_box(p - vec3f(2.5, 0.0, 0.0), vec3f(0.8)), 3.0));
    return d;
}

Then resolve the material once, after the march, in a single switch. Doing it inside the loop would evaluate every material branch on every step for every pixel in the group.

Other quantities that come free from the march

  • Depth / fog: t is a true world-space distance, so exp(-t * density) is physically meaningful atmospheric falloff, unlike the z-buffer value a rasterizer gives you.
  • Iteration count: the number of steps taken correlates with proximity to silhouettes and creases. Divided by MAX_STEPS it makes a serviceable cheap ambient occlusion and an excellent profiler.
  • Curvature: the Laplacian, (sum of the 4 tetrahedron taps) − 4·map(p), is positive on convex ridges and negative in concave valleys. Free if you already computed the normal — reuse the taps.
  • UVs: there are none. Use triplanar projection (blend three world-axis-aligned samples by the squared normal components) or object-space coordinates captured before your domain transforms.

Step 6 — light, by marching more

Shadows and occlusion are the same loop pointed somewhere else

This is the compensation for all the work in section 5: effects that require multi-pass machinery in a rasterizer are a dozen lines here, because you can query visibility from any point in any direction on demand.

Soft shadows for the price of a hard one

March from the surface toward the light. Instead of only asking whether anything blocks the ray, track how close the ray came to blocking — the smallest ratio of clearance to distance travelled. That ratio is the angular size of the gap, which is exactly what determines penumbra width.

wgslQuilez soft shadow, banding-corrected variant
fn soft_shadow(ro: vec3f, rd: vec3f, t_min: f32, t_max: f32, k: f32) -> f32 {
    var res = 1.0;
    var t = t_min;
    var prev_h = 1e20;

    for (var i = 0; i < 48; i++) {
        let h = map(ro + rd * t).x;

        // estimate the closest approach across the segment, not just at samples
        let y = h * h / (2.0 * prev_h);
        let d = sqrt(max(h * h - y * y, 0.0));
        res = min(res, k * d / max(0.0, t - y));

        prev_h = h;
        t += clamp(h, 0.01, 0.35);
        if (res < 0.004 || t > t_max) { break; }
    }
    res = clamp(res, 0.0, 1.0);
    return res * res * (3.0 - 2.0 * res);   // smoothstep the falloff
}

k is the inverse angular radius of the light: k = 32 is a small crisp source, k = 4 is a broad overcast one. Start the ray at t_min ≈ 2·ε or a few times your normal's h, or the surface shadows itself and everything turns black.

Ambient occlusion by walking up the normal

Step a short way along the normal and compare where you are with what the field says. If the field reports less distance than you travelled, something nearby is occluding you.

wgsl5-tap AO
fn ambient_occlusion(p: vec3f, n: vec3f) -> f32 {
    var occ = 0.0;
    var weight = 1.0;
    for (var i = 0; i < 5; i++) {
        let h = 0.01 + 0.12 * f32(i) / 4.0;
        let d = map(p + n * h).x;
        occ += (h - d) * weight;
        weight *= 0.92;                    // nearer samples matter more
    }
    return clamp(1.0 - 2.5 * occ, 0.0, 1.0);
}

Putting a frame's worth of shading together

wgsla complete, minimal fs_main body
let hit = march(ro, rd);
var col = sky(rd);

if (hit.id > 0.0) {
    let p   = ro + rd * hit.t;
    let n   = calc_normal(p, max(0.5 * px * hit.t, 1e-4));
    let l   = normalize(vec3f(0.6, 0.7, -0.4));

    let ao  = ambient_occlusion(p, n);
    let sha = soft_shadow(p + n * 0.02, l, 0.02, 30.0, 16.0);

    let diffuse = max(dot(n, l), 0.0) * sha;
    let sky_fill = (0.5 + 0.5 * n.y) * ao;                 // hemisphere ambient
    let bounce  = max(dot(n, vec3f(0.0, -1.0, 0.0)), 0.0); // fake floor bounce

    let albedo = material_albedo(hit.id, p, n);
    col = albedo * (diffuse * vec3f(1.3, 1.1, 0.85)
                  + sky_fill * vec3f(0.28, 0.36, 0.5)
                  + bounce * 0.15);

    col = mix(col, sky(rd), 1.0 - exp(-0.00015 * hit.t * hit.t * hit.t)); // fog
}

col = pow(col, vec3f(0.4545));            // gamma, if your target is not *_srgb
return vec4f(col, 1.0);
Gamma

Do the encode or use an sRGB surface format, never both. If surface_format is Bgra8UnormSrgb the hardware converts for you, and adding pow(col, 1/2.2) on top washes everything out. surface.get_capabilities(&adapter).formats[0] is frequently the sRGB variant, so check rather than assume.

Step 7 — fields that aren't distance fields

What to do when you can't write a distance function

Distance functions are convenient, not required. Plenty of interesting geometry has no closed-form distance — noise isosurfaces, algebraic surfaces, volumetric data, fractals. The pattern is always the same: find a valid step bound, or give up on bounds and step small enough to catch what you care about.

Implicit surfaces · f(p) = 0

A gyroid, a torus written algebraically, a metaball sum. The magnitude of f is meaningless as a distance, but the first-order estimate is not:

d ≈ f(p) / ‖∇f(p)‖

That's one Newton step toward the root. If you can bound ‖∇f‖ analytically, divide by the bound instead and the estimate becomes conservative — safe to sphere trace. For a gyroid, ‖∇f‖ ≤ √3.

Escape-time fractals

Mandelbulbs and Julia sets have no distance function, but they have a distance estimator derived from the running derivative of the iteration:

DE = 0.5 · log(r) · r / dr

It underestimates in some regions and overestimates in others. Step by 0.5–0.8 × DE, raise MAX_STEPS toward 256, and expect a costly shader.

Volumes and participating media

No surface exists, so there is nothing to converge to. Fixed steps, accumulate transmittance, jitter the start offset per pixel to convert banding into noise you can then denoise or temporally accumulate. Budget for a nested light march at every sample — that's where the cost is.

Heightfields

Only one dimension of the field matters. March in the ground plane and compare p.y to height(p.xz). Grow the step with distance so the sample density stays roughly constant on screen. Refine with interpolation, and note the normal comes from the 2D gradient of height, not a 3D tetrahedron.

Analytic primitives

If the geometry is a sphere, plane, box, or cylinder, don't march it — solve it. A ray/sphere test is a quadratic. Mixing analytic and marched geometry in one pass is normal: solve the analytic ones, march the rest, keep whichever t is smaller.

Voxels / 3D textures

A DDA traversal steps exactly cell-to-cell with no sampling error and no missed voxels — strictly better than fixed-step marching through a grid. In WGSL, sample the volume with textureSampleLevel, not textureSample, since you're inside non-uniform control flow.

Root refinement, when the sign flips

Both the implicit-surface and heightfield cases reduce to the same problem: you have f(t₀) > 0, f(t₁) < 0, and want the crossing. Linear interpolation is one line and usually enough. Bisection is exact to any precision you're willing to pay for, and unlike Newton's method it cannot diverge.

wgslboth refinements
// cheap: secant / regula falsi, one evaluation already done
let t_hit = mix(t0, t1, f0 / (f0 - f1));

// robust: bisection, 8 iterations halves the interval 256x
var a = t0;
var b = t1;
for (var i = 0; i < 8; i++) {
    let m = 0.5 * (a + b);
    if (field(ro + rd * m) > 0.0) { a = m; } else { b = m; }
}

Step 8 — bounding the work

The cheapest step is the one you never take

A raymarcher's cost is pixels × steps × cost of map(). All three are attackable, and the first two are usually easier than optimizing the field.

Clip the march to a bounding volume

Intersect the ray with an analytic box around your scene first. Rays that miss return immediately; rays that hit start at the near intersection instead of the camera and stop at the far one. On a scene occupying a corner of the frame this is a large win for almost no code.

wgslslab method — branchless, all three axes at once
// returns (t_near, t_far); miss if t_far < max(t_near, 0.0)
fn box_interval(ro: vec3f, rd: vec3f, lo: vec3f, hi: vec3f) -> vec2f {
    let inv = 1.0 / rd;                       // inf on axis-aligned rays is fine
    let a = (lo - ro) * inv;
    let b = (hi - ro) * inv;
    let t_lo = min(a, b);
    let t_hi = max(a, b);
    return vec2f(
        max(max(t_lo.x, t_lo.y), t_lo.z),
        min(min(t_hi.x, t_hi.y), t_hi.z)
    );
}
The 0 × ∞ case

If a ray component is exactly zero and the origin sits exactly on the corresponding slab plane, inv is infinity and the product is NaN. In practice the componentwise min/max absorbs it on most hardware, but WGSL does not guarantee NaN behaviour for these builtins. If you see single black pixels on axis-aligned camera angles, nudge rd away from exact zeros: rd + vec3f(1e-8).

Render at lower resolution

The march is per-pixel and the cost is roughly linear in pixel count, so rendering to a half-resolution texture and upscaling is close to a 4× speedup. Raymarched images are typically low-frequency enough that this is far less visible than it would be on rasterized geometry. Do the march into an offscreen Rgba16Float target, then run a second trivial fullscreen pass to blit and tone-map. That second pass is also where post effects, sharpening and temporal accumulation belong.

Make map() cheaper, not just shorter

  • Bound before you evaluate. Wrap expensive sub-objects in a cheap bounding sphere: if (bound > 0.5) { return bound; } before evaluating the detailed part. This is the single biggest win in complex scenes.
  • Fold the domain instead of instancing. p - s * round(p / s) gives infinite repetition at zero cost. Clamp the repetition index to get a finite grid without a loop.
  • Cache invariants outside the loop. Anything depending only on time — rotation matrices, animation curves — computes once per pixel, not once per step.
  • Watch out for divergence. Two adjacent pixels taking 8 and 120 steps both cost 120, because they execute together. Grazing angles and silhouettes are where this happens; a step-count heatmap shows it instantly.

Step 9 — living with the rasterizer

Writing depth so marched and triangle geometry intersect properly

By default your fullscreen triangle writes whatever depth the vertex shader emitted, which is meaningless. To let raymarched surfaces occlude and be occluded by ordinary meshes, output @builtin(frag_depth) computed from the actual hit position.

wgsldepth output
struct FsOut {
    @location(0) color: vec4f,
    @builtin(frag_depth) depth: f32,
};

@fragment
fn fs_main(@builtin(position) pos: vec4f) -> FsOut {
    // ... build ray, march ...
    var out: FsOut;

    if (hit.id < 0.0) {
        out.color = vec4f(sky(rd), 1.0);
        out.depth = 1.0;                       // far plane; 0..1 in WebGPU
        return out;
    }

    let world = ro + rd * hit.t;
    let clip  = u.view_proj * vec4f(world, 1.0);
    out.depth = clip.z / clip.w;               // already in [0,1], no remap
    out.color = vec4f(shade(world, hit), 1.0);
    return out;
}

The matching pipeline needs a real depth attachment:

rustdepth state
depth_stencil: Some(wgpu::DepthStencilState {
    format: wgpu::TextureFormat::Depth32Float,
    depth_write_enabled: true,
    depth_compare: wgpu::CompareFunction::Less,
    stencil: Default::default(),
    bias: Default::default(),
}),
Cost

Writing frag_depth disables early depth testing for the whole pipeline — the GPU can't reject a fragment before running a shader that decides its own depth. For a fullscreen pass that's usually irrelevant, since nothing was going to reject it anyway. But it means you cannot use previously rendered depth to skip marching. If you want that, draw opaque meshes first, sample the depth buffer as a texture in the raymarching pass, and clamp MAX_DIST to the reconstructed view distance.

Order of operations

  1. Render opaque triangle geometry into colour + depth as usual.
  2. Run the raymarching pass with depth_compare: Less and depth writes on. Marched surfaces behind meshes get rejected after shading; marched surfaces in front win.
  3. Run any volumetric pass last, with depth writes off and alpha blending on, using the depth buffer to terminate each ray at the first solid surface.

Hot reload is not optional

Raymarching is iterative by nature — you tune constants by looking at the result. Watch the .wgsl file with notify, rebuild the shader module and pipeline on change inside a validation error scope, and keep the old pipeline on failure. Ten minutes of setup pays for itself the first evening.

An order of operations for building one from scratch

  1. Fullscreen triangle. Output vec4f(uv, 0.0, 1.0) and confirm the gradient runs the direction you expect — this catches the y-flip immediately.
  2. Ray generation. Output rd * 0.5 + 0.5. You should see a smooth colour field that rotates with the camera.
  3. March against a single sphere at the origin. Output the step-count heatmap, not shading.
  4. Normals. Output n * 0.5 + 0.5 and check for speckle before adding any light.
  5. One directional light, no shadows. Now the image is legible and every subsequent bug has a visible cause.
  6. Ground plane, then shadows, then AO, then fog — in that order, checking the heatmap after each.

Every step in that list is verifiable on its own. The single most common way to lose an evening is writing all six at once and then trying to work out which of them is wrong.
